# contract-platform

Генератор договоров для Медиа Лэнд: FastAPI + PostgreSQL + MinIO + React,
всё в Docker Compose на VPS. Русскоязычные юридические документы (.docx)
по шаблонам с метками, данные подставляются из карточек контрагентов.

Общение — по-русски.

## Деплой — КРИТИЧНО

**Автоматический.** В bare-репо на сервере (`~/git/contract-platform.git`) есть рабочий хук
`post-receive`, который сам раскладывает файлы в `~/contract-platform` после пуша.
**Ручной `git --git-dir=... --work-tree=... checkout` НЕ нужен** (раньше ошибочно
считался обязательным — это не так, проверено).

Два remote, **пушить всегда в оба**:
```bash
git push origin main && git push production main
```

Полный цикл правки:
```bash
# 1. если менялся фронт — пересобрать (иначе прод увидит старую сборку):
cd frontend && ./deploy.sh && cd ..

# 2. закоммитить И исходники, И сборку:
git add <файлы> backend/static/app
git commit -m "..."
git push origin main && git push production main

# 3. ТОЛЬКО если добавлена миграция:
ssh root@64.188.98.101 "cd ~/contract-platform && docker compose exec api alembic upgrade head"
# затем убедиться, что воркер перезапустился на новой схеме (см. ниже про окно):
ssh root@64.188.98.101 "cd ~/contract-platform && touch backend/app/main.py"
```

Что хук НЕ делает:
- **не накатывает миграции** — всегда отдельным шагом, вручную;
- не перезапускает контейнеры — не нужно: `backend/app`, `backend/static`, `backend/alembic`
  смонтированы как volume, `uvicorn --reload` подхватывает правки сам.

**Подводный камень: окно «код ↔ миграция» (инцидент 16.07.2026).** Пуш деплоит
код мгновенно (volume + `uvicorn --reload`), а миграцию накатывают отдельным
шагом ПОСЛЕ. Поэтому между пушем и `alembic upgrade` воркер уже работает на
новом коде со СТАРОЙ схемой БД: если новый код читает/пишет добавленную колонку,
он падает на старте (`Application startup failed. Exiting.`) до накатки миграции.
Reloader при этом жив (контейнер `Up`), но воркер не перезапустится сам, пока не
изменится watched-файл. Порядок для миграций, где код уже использует новое поле:
1. `git push …` (код уедет и воркер, возможно, временно упадёт — это ожидаемо);
2. `alembic upgrade head`;
3. `touch backend/app/main.py` — триггерит `--reload`, воркер поднимается на
   новой схеме. Проверить `docker compose logs --tail=6 api` → «Application
   startup complete». Для аддитивной nullable-колонки это лишь ~минута простоя;
   для несовместимых изменений схемы планировать деплой аккуратнее.

**Почему сборка React лежит в git.** На сервере нет Node — собрать там нечем.
`backend/static/app/` попадает в контейнер через уже существующий volume на
`backend/static`, поэтому ни `docker-compose.yml`, ни пересборка образа не нужны.
Это осознанное решение, а не недосмотр.

**Правило после инцидента 15.07.2026**: недоделанный React выложили поверх
`backend/static/index.html` и сломали вход на проде. Поэтому старый интерфейс живёт
на `/`, новый — на `/app`. Не заменять `index.html` без явной просьбы: это откат
в один клик, если что-то пойдёт не так.

## Бэкапы (сделано 17.07.2026)

Два слоя. Раньше не было ни одного: карточки контрагентов существовали в
единственном экземпляре.

**Слой 1 — на сервере.** `ops/backup.sh`, cron root'а в 00:30 UTC (03:30 MSK),
кладёт в `/root/backups`, ротация 14 дней, лог `/var/log/contracts-backup.log`.
Спасает от кривого SQL и случайно удалённой карточки (`DELETE` физический).
От смерти диска не спасает — он на той же машине.

**Слой 2 — на ПК разработчика.** `ops/pull-backup.ps1`, планировщик Windows
в 14:00 MSK, репозиторий restic на `D:\Backups\contract-platform`, ключ и
пароль в `%USERPROFILE%\.contracts-backup`. Retention: 14 дней / 8 недель /
12 месяцев.

Время дневное намеренно: ночью ПК выключен, а задача работает только при
вошедшем пользователе (см. ниже). К 14:00 серверный дамп от 03:30 MSK готов
давно — порог свежести 48 ч, запас десятикратный.

Неочевидное, на чём легко обжечься:

- **Дамп в plain и tar без сжатия — намеренно.** Их забирает restic, а сжатие
  убивает дедупликацию: один изменённый байт меняет весь файл. Проверено —
  вторая точка восстановления стоит 3 КБ вместо 535.
- **Шаблоны выгружаются через `app.storage`, а не tar'ом volume'а MinIO.**
  MinIO хранит объекты как `<uuid>.docx/xl.meta`, мелкие — вшиты прямо в
  метаданные, `part.1` не существует. Копию volume'а можно вернуть только в
  MinIO; открыть договор из неё нельзя. Рядом кладётся `templates-*.txt` —
  расшифровка uuid → название.
- **Тянем, а не толкаем.** Сервер не знает адреса копии. Ключ ограничен через
  `command=` в `authorized_keys` → `ops/serve-backup.sh`: отдать
  `/root/backups` и ничего больше. Ключ без парольной фразы (планировщику
  иначе никак), но root-шелла не даёт — проверено, `ssh ... id` не выполняется.
- **`ssh -i` без `IdentitiesOnly=yes` берёт ключ из агента** и ходит
  полноправным root мимо ограничения. На этом я попался при проверке.
- **PowerShell портит бинарный поток при `>`** (пишет UTF-16) — скачивание
  только через `cmd /c`. И `ssh` из PowerShell зависает на stdin: нужен
  `ssh -n` либо `cmd /c`.
- **`.ps1` обязан быть UTF-8 С BOM** — PowerShell 5.1 без BOM читает как ANSI,
  кириллица рассыпается, скрипт не парсится. `.gitattributes` держит `*.sh` в LF
  по той же причине (CRLF → `bad interpreter: ^M`).
- **Задача в планировщике — Interactive**, то есть работает только когда
  пользователь вошёл (S4U требует прав админа, отказано). `StartWhenAvailable`
  догоняет пропущенный запуск. Это принятое слабое место: ПК выключен —
  копий нет.
- **Запуск скрытый — через `ops/run-backup-hidden.vbs`, а не powershell напрямую.**
  Действие задачи: `wscript.exe "…\ops\run-backup-hidden.vbs"`, а уже VBS
  зовёт `pull-backup.ps1` через `.Run(cmd, 0, True)`. Почему не проще
  `powershell.exe -WindowStyle Hidden`: та всё равно на миг создаёт окно
  консоли и ВОРУЕТ ФОКУС (сворачивает другие окна) — на это и жаловались
  31.07.2026. `wscript` с окном стиля 0 не показывает ничего вообще; `True`
  в третьем аргументе + `WScript.Quit rc` дожидаются ps1 и пробрасывают её
  код выхода, поэтому «последний результат» задачи по-прежнему отражает успех
  бэкапа, а не запускалку. Путь к .ps1 VBS берёт рядом с собой (ScriptFullName),
  не хардкодит — переезд папки не ломает. При пересоздании задачи (новый ПК)
  действие должно указывать на VBS, а не на powershell.
- **Отказ виден**: при ошибке появляется `D:\Backups\БЭКАП-СЛОМАН.txt`, при
  успехе исчезает. Скрипт сам проверяет, что свежему дампу не больше 48 ч —
  тихо сломавшийся cron это и есть авария.
- **Пароль restic потерять = потерять репозиторий.** Лежит в
  `%USERPROFILE%\.contracts-backup\restic-password.txt`, обязан быть ещё и в
  менеджере паролей.

### Восстановление и проверка — `ops/restore.sh`

Зеркало `backup.sh`. Роняет схему `public` (в дампе нет ни одного `DROP` —
`pg_dump --format=plain` без `--clean`, рассчитан на пустую базу) и
разворачивает дамп; вычищает бакет MinIO и раскладывает шаблоны из архива
через тот же `app.storage`. **`.env` не восстанавливает** — он нужен раньше,
чем что-либо поднимется (без него не стартует ни `docker compose`, ни база),
класть на место руками ДО запуска (лежит рядом с дампом, `env-<дата>.txt`).
**Alembic после restore НЕ накатывать** — в дампе финальная схема и своя
строка в `alembic_version`; схему приносит дамп, а не миграции.

**Регулярная проверка бэкапа (раз в месяц), не трогая прод:**
```bash
ssh root@64.188.98.101
cd ~/contract-platform
DB_NAME=contracts_test BUCKET=test-restore ops/restore.sh latest --yes
# прибрать за собой:
docker compose exec -T db dropdb -U contracts_app contracts_test
```
`DB_NAME`/`BUCKET` уводят восстановление в отдельную базу и бакет — боевые
`contracts` и бакет из `.env` не затрагиваются, api не останавливается (это
делается только в боевом режиме). Скрипт разворачивает свежий бэкап и печатает
`=== Результат ===`: число контрагентов, пользователей, шаблонов, записей
истории, **меток с настроенным maps_to** и версию схемы — они должны совпасть с
боевыми; плюс сверяет, что шаблонов в бакет легло ровно столько, сколько в
архиве (иначе выходит с ошибкой). Смысл проверки: убедиться, что свежий дамп
действительно разворачивается и в нём есть всё, включая `template_fields` —
настройку автоподстановки, которую при переезде теряют чаще всего. Бэкап, из
которого ни разу не восстанавливали, — это просто файл.

Прогонялось по-настоящему (17.07.2026): восстановление в `contracts_test`
дало ровно боевые числа (7/3/14/30, 30 меток maps_to, схема `a1f0c8e5d3b7`),
16 шаблонов из 16; боевые база и api при этом целы. Также: md5 карточек и
payload истории совпадали с боевыми, файлы из restic сходятся по sha256,
.docx из архива открывается.

### Переезд на другой сервер

Дамп переносит **всё**, ручной сборки по частям не требуется:
аккаунты — вместе с паролями (argon2-хэш самодостаточен, ничего не хранится
снаружи строки), историю генерации, журнал, папки и настройку maps_to.
Импорт/экспорт в Excel для переезда НЕ годится: он переносит две таблицы из
десяти (`contragents` + никнеймы), а `template_fields` (166 строк, из них
настроенных maps_to — 30) руками не восстановить, и автоподстановка молча
исчезнет.

1. Новый сервер: docker + папка проекта (или `git clone`).
2. Скопировать `.env` (его нет в git!) и файлы из `/root/backups`.
3. `docker compose up -d db minio`
4. `ops/restore.sh latest` → ввести `ВОССТАНОВИТЬ`.
5. `docker compose up -d`

только файлом. Поэтому импорт партнёров вынесен в своё право
(`CAN_IMPORT_PARTNERS`), а выгрузка каталога ей открыта.
- **БАЛАНСОВ ОНА НЕ ВИДИТ** (`CAN_VIEW_BALANCES`, 19.09.2026): вкладка
  «Контрагенты» ей нужна как справочник — реквизиты, псевдонимы, треки, — а
  сколько кому выплачено, нет. Сервер таких чисел ей и не присылает: в списке
  нет колонки баланса, в карточке — блока с суммами и операциями. Право
  отдельное, а не «если не финансовый менеджер»: баланс — самостоятельное
  знание, и закрывать его придётся однажды не только этой роли.
- **ДОСТИЖЕНИЙ У НЕЁ НЕТ** (`CAN_HAVE_ACHIEVEMENTS = DOCS_ROLES`): они
  считаются по работе с документами, и получать их ей не за что. Раздел в
  профиле скрыт, точка у имени не загорается, `GET /profile/achievements`
  отвечает 403 — пустой список читался бы как «пока ничего не набрал».
- **`DOCS_ROLES` в `roles.py`** — «все роли, кроме финансового менеджера».
  Документные права (генерация, создание и правка карточек, история
  генерации, кубок) считаются ОТ НЕЁ, а не от `ROLES`. Почему не
  перечислением: `= ROLES` там стоит намеренно, чтобы новая роль получала
  права сама собой — на перечислении однажды уже погорели (tester не мог
  сгенерировать документ). С появлением роли, которой ML Docs не положен,
  «все роли» и «все, кто работает с документами» разошлись, и разделять их
  надо было явно. Новая роль ML Docs по-прежнему получает всё сама;
  новая роль второго продукта добавляется в исключение одной строкой.
- **Экраны ML Docs закрыты и по прямому адресу** (`canUseDocs` в `App.jsx`):
  раньше `/search`, `/database`, `/folders` и форма генерации были открыты
  любому залогиненному — других ролей, кроме документных, не существовало.
- **ИНСТРУКЦИЯ В ПРОФИЛЕ РАЗДЕЛЕНА ПО ПРОДУКТАМ** (`content/guide.js`,
  19.09.2026). Разделы ML Docs помечены `roles: DOCS`, финансовые — `FINANCE`
  (три вкладки) и `FINANCE_FULL` (плюс отчёты, поступления, правка каталога и
  операции). Раньше все документные разделы шли без ролей, то есть «всем», —
  и финансовый менеджер получил бы инструкцию по генерации договоров и ни
  слова про свои вкладки. ML Finance расписан по разделу на вкладку: обзор,
  номенклатура, правка каталога, контрагенты и балансы, операции, партнёры,
  отчёты площадок, поступления. Группы ролей заданы списками в начале файла —
  перечислять их в каждом из двадцати разделов значит однажды забыть.
- **В окне входа больше нет ни названия продукта, ни описания** (просьба
  владельца 19.09.2026): за одной формой теперь два продукта, и встречать
  финансового менеджера вывеской «ML Docs» неправильно. Куда человек
  попадёт, решает его роль.

⚠️ **Сейчас `top_manager` и `manager` не отличаются НИЧЕМ** (сверено с кодом
10.09.2026, матрица считается из `roles.py`). Правка заведённых карточек была
единственным отличием топ-менеджера, и она временно открыта всем (строка
`⚠️врем.` в таблице, см. `CAN_EDIT_CONTRAGENTS` ниже); экспорт и скрытые
шаблоны у него убрали раньше. Пока послабление действует, единственная роль
ниже директора, которая реально что-то добавляет, — `tester`. Проверять это
утверждение заново после любой правки ролей: разойтись легко.

`director` — почти как `admin` по чтению/правке: правка карточек, экспорт,
audit_log, вся история генерации и **просмотр** вкладки «Пользователи» (только
видит список и роли — не создаёт, не меняет роли: это осталось за admin, см.
`CAN_VIEW_USERS` / `CAN_MANAGE_USERS`). Без импорта, управления шаблонами и
удаления контрагентов.

`top_manager` — ЗАДУМАН как `manager` плюс редактирование карточек; экспорт и
скрытые шаблоны у него убраны. Фактически сейчас полностью совпадает с
`manager` — см. предупреждение выше.

`tester` — **самостоятельная роль** (раньше повторяла `top_manager` — эта
зависимость снята). Как `manager`, плюс редактирование карточек, кнопка
«Тестовые данные» и просмотр скрытых шаблонов (всё для обкатки). Без экспорта.
Кнопка демо живёт в `canFillDemoData` (permissions.js) и серверной проверки не
имеет — демо-данные не привилегия.

**Вкладка «История генерации» — у ВСЕХ ролей** (решение владельца 08.08.2026):
каждый видит СВОЮ генерацию. admin/director — всю
(`SEES_ALL_GENERATION_HISTORY`), остальные (top_manager/tester/manager) — только
свои документы, сервер ограничивает выдачу по `user_id`
(`CAN_VIEW_GENERATION_HISTORY = ROLES`). **Удаление записей истории — только
admin** (`CAN_DELETE_GENERATION_HISTORY`, `DELETE /generation-history/{id}`),
для чистки тестовых записей; кнопка удаления в строке видна только ему.

`manager` — генерация и создание контрагентов. **ВРЕМЕННО (с 04.08.2026) правит
карточку целиком**, кроме титла: `CAN_EDIT_CONTRAGENTS = ROLES` на период
массового заполнения базы. Откат — ровно две строки (кортеж в `roles.py` и
`canEditContragents` в `permissions.js`).

Когда послабление снимут, у менеджера НАВСЕГДА останутся отдельные поля: тип
договора (`contract_family` — нужен для подбора документов), реквизиты, рег.
номер, номер договора и псевдонимы — у каждого своё право `= ROLES`
(`CAN_EDIT_CONTRACT_FAMILY`, `CAN_EDIT_REQUISITES`, `CAN_EDIT_REG_NUMBER`,
`CAN_EDIT_CONTRACT_NUMBER`, `CAN_EDIT_NICKNAMES`). Реализовано полем-уровнем в
`update_contragent`: эндпоинт открыт всем ролям, но передача поля, на которое
права нет, даёт 403; ограниченный режим модалки (`EditContragentModal.restricted`)
включится сам, как только `manager` выйдет из `CAN_EDIT_CONTRAGENTS`.

Новая роль **не требует миграции**: `users.role` — обычный `varchar(16)` без
ограничения в БД, значение проверяется приложением против `ROLES`. Следить
надо лишь за длиной строки (≤16 символов).

**Скрытие шаблонов от менеджеров** (`templates.hidden_for_managers`, добавлено
для обкатки шаблонов до показа рабочим менеджерам). Скрытый шаблон роль
`manager` НЕ видит в дереве папок и в подборе по контрагенту и не может его
сгенерировать (404, а не 403 — для менеджера он «не существует»). Видят и
генерируют его admin/director/tester (`SEES_HIDDEN_TEMPLATES` в `roles.py`;
top_manager по этому праву теперь как manager — не видит); переключает флаг только admin
(`PATCH /templates/{id}/visibility`, тумблер в модалке настройки шаблона). Это
не UX-заглушка, а серверная проверка в трёх местах: `browse_folder`,
`list_contragent_templates`, `get_template_fields`/`generate_document`. В дереве
у скрытого шаблона бейдж «скрыт» — его получают только те роли, что вправе
видеть скрытое.

Права на фронте — только UX (не показывать кнопку, которая вернёт 403).
Настоящая защита всегда на сервере: `Depends(require_role(...))`.

Админ **не может** сменить роль себе или деактивировать себя (400) — иначе
единственный админ запер бы себя снаружи безвозвратно.

## Ключевые принципы (нарушать только осознанно)

**Форма генерации строится из .docx, а не из кода.** `template_analysis.analyze_template()`
сканирует метки (`{{ x }}`, `{% for %}`, `{% if %}`) и выводит тип поля
(text/date/flag/choice/list). Добавили метку в шаблон → поле появилось в форме само.
В `DocFormPage.jsx` нет ни одного захардкоженного поля — так и должно остаться.
Поэтому новые типы контрагентов (ИП, ООО с НДС) не требуют правок фронта.

**maps_to — это предзаполнение, а не подстановка.** `GET /templates/{id}/fields?contragent_id=...`
кладёт значения из карточки в `default`. `POST /generate` их не проверяет и не
перезаписывает: единственный источник истины для документа — то, что реально пришло
в теле запроса. Оператор может поправить любое подставленное значение.

**Справочники — только с сервера.** Страны, типы контрагентов, типы договоров, роли,
`reg_number_meta` (ИНН/ОГРНИП/ОГРН + длины) приходят из `GET /tags`. Фронт их не
хардкодит: бэкенд теми же значениями валидирует, любое расхождение = 400 при сохранении.

**reg_number — одна колонка на три смысла.** ИНН (СГ, 12 цифр) / ОГРНИП (ИП, 15) /
ОГРН (ООО, 13). Какой именно — определяет поле `type`, отдельных колонок нет.
**НЕ уникален** (11.08.2026, разворот прежнего `unique=True`): у одного человека
карточки на аванс и роялти делят один ИНН/ОГРНИП, поэтому дубли рег.номера — норма,
UNIQUE снят (индекс остался), все проверки конфликта убраны. Валидируется только
формат (длина/цифры под тип, `normalize_reg_number`).

**Уникальный идентификатор контрагента — `dista_id`** (наш код из Dista Music, у
него UNIQUE), а НЕ reg_number и НЕ title (оба не уникальны). Именно `dista_id` —
надёжный ключ правки и **главный ключ импорта**: импорт матчит строку по колонке
«Dista ID» (первая в шаблоне), запасной ключ — титл (нужен только для новой
карточки). Импорт также проставляет/привязывает `dista_id` к карточке.

**Защита от дублей при создании — на СЕРВЕРЕ и по вычисленному титлу**
(10.09.2026, после инцидента). `POST /contragents` считает
`build_contragent_title(ФИО, тип)` и ищет карточки с таким же титлом
(`_find_title_duplicates`: сравнение без учёта регистра и ВСЕХ пробелов — в базе
лежат и «Куликов И.М. (СГ)», и «Куликов И.М.(СГ)»). Нашлись → **409**
`detail={code:'duplicate_title', message, duplicates:[{id,title}]}`; повторный
запрос с `confirm_duplicate=true` создаёт карточку и пишет в audit_log
`meta.duplicate_confirmed` — видно, с чем согласился оператор. На фронте это
модалка `confirmDuplicateContragent` («Всё равно создать»).

Почему подтверждение, а не запрет: титл — это фамилия + инициалы + тип, и
«Иванов И. И. (СГ)» законно бывают двумя РАЗНЫМИ людьми; вторая карточка на
того же человека под аванс/роялти тоже норма (см. выше про title).

Почему титл, а не ФИО: **у 465 из 828 боевых карточек `name` пустой** (пришли
импортом, есть только сокращённый титл). Прежняя проверка жила только на фронте
и сверяла `c.name` — против импортных карточек не срабатывала в принципе, да и
искала их по подстроке полного ФИО («Кеосеян Эдгар Зареевич»), которой в титле
«Кеосеян Э. З. (ИП)» нет. Обе половины промахнулись → дубль создался молча
(09.09.2026). Не ловится до сих пор: дубль с титлом в другом формате («ООО
Золотой звук» против вычисленного «Золотой звук (ООО)») — на это есть мягкая
подсказка «похожие уже есть» в форме, она ищет по ПЕРВОМУ СЛОВУ (фамилии), а не
по полному ФИО. `apiJson` кладёт код ответа и объектный `detail` в `err.status`
/ `err.detail` — иначе 409 не отличить от 400 по одному лишь тексту.

**title и contract_number вычисляются ТОЛЬКО при создании карточки и приходят
импортом — при правке карточки НЕ пересчитываются** (31.07.2026, разворот
решения от 16.07.2026). Руками в форме правки они не редактируются (полей нет),
`PATCH` их больше не пересобирает по ФИО/типу/дате. Причина разворота: все титлы
уже соответствуют существующей базе компании, а **старые номера договоров
собраны по ДРУГОЙ формуле**, чем `build_contract_number()` — пересчёт задним
числом разошёлся бы с уже подписанными документами. Поэтому единственные пути
изменить title/номер: импорт из Excel (массово) или явно переданное значение в
`PATCH` (ручной override, через UI недоступен — форма их не шлёт). Ручной
override title всё ещё нужен, чтобы различать две карточки одного человека на
разные `contract_family` («Иванов И. И. (СГ, аванс)» / «(СГ, роялти)»), но задаётся
он теперь импортом, а не правкой ФИО.

⚠️ Прежнее (16.07.2026) поведение «PATCH пересобирает title при смене ФИО, а
contract_number — при смене ФИО/типа/даты» ОТМЕНЕНО. Если встретишь в старом
контексте упоминание автопересчёта при правке — оно неактуально.

**Аванс выплачивается частями, и пустые пункты в договор не печатаются**
(17.09.2026, договоры «аванс + обязательство на треки», СГ и ИП). Общая сумма
(`advance`) делится на три части со своими пунктами: до сдачи треков
(`advance_first`), после сдачи половины (`advance_middle`) и после сдачи всех
(`advance_end`). Обычная выплата — в две части, поэтому пункт с пустой или
нулевой суммой не печатается вовсе: «0 рублей после сдачи всех треков» в
договоре читается как ошибка.
- **Номера пунктов подставляются, а не набраны в шаблоне** (`clause_first` /
  `clause_middle` / `clause_end`, считает `build_advance_parts` в
  `context_builder`). Набери шаблон «2.2.2/2.2.3/2.2.4» сам — при выпавшей
  середине осталось бы «2.2.2, 2.2.4», то есть дырка в нумерации. Сервер
  раздаёт номера подряд по заполненным частям.
- **Номер и условие — ОДНА метка.** В шаблоне абзац обёрнут в
  `{%p if clause_first %}`, а внутри печатает `{{ clause_first }}`. Две
  похожие метки (отдельно «показывать» и отдельно «номер») рано или поздно
  разъехались бы местами.
- **Пустая часть = пункта нет, и сервер её не требует.** В `generate_document`
  метки скрытого пункта добавляются в `optional` — ровно как `smm/smm_text`
  при выключенной галочке «Маркетинговая кампания». Иначе проверка
  обязательных полей требовала бы заполнить то, чего в документе не будет.
- **ПРЕДЗАПОЛНЕНИЕ ЖИВЁТ В ФОРМЕ, А НЕ НА СЕРВЕРЕ** (`computeAdvanceHalves` /
  `computeCountMiddle` в `DocFormPage.jsx`, рядом с `computePenalty`). Как
  только заполнены «Сумма аванса» и «Количество треков», форма делит аванс
  пополам (лишний рубль — в первую часть, чтобы сумма сошлась) и ставит
  `count_middle` = половина треков с округлением ВВЕРХ (в договоре «не
  менее»). Считай это сервер — убрать часть выплаты стало бы нечем: он
  заполнял бы обратно ровно то поле, которое очистили.
  - **Пометка «тронуто» здесь ставится и на ОЧИСТКУ поля**, в отличие от
    `penalty`/`term_end`, где пусто значит «считай сам». Пустая часть аванса —
    осмысленный ответ («такой выплаты нет»), и спорить с ним форма не должна.
  - Правка любой из трёх частей останавливает предзаполнение всех: как делить
    сумму — одно решение, а не три.
- **ЧАСТИ ОБЯЗАНЫ СХОДИТЬСЯ С ОБЩЕЙ СУММОЙ, и это проверяется при
  формировании документа** (`advance_parts_problem`, просьба владельца
  17.09.2026). Договор, где в п. 2.2 стоит «задаток 150 000», а ниже
  перечислено 135 000, противоречит сам себе, и глазами это не ловится —
  числа в разных абзацах. Отказ приходит текстом с обеими суммами
  («75 000 + 60 000 = 135 000 ₽, а сумма аванса — 150 000 ₽») и показывается
  тем же окном, что и «не заполнены обязательные поля».
  - **Проверка ОДНА и живёт на сервере**, хотя половины считает форма: тот
    же расчёт в двух местах рано или поздно разъедется, а пропустить его
    нельзя ни из интерфейса, ни при прямом вызове API.
  - **Молчит, когда сумма аванса пуста или не число**: про это точнее скажут
    проверка обязательных полей и разбор суммы, а два сообщения об одном и
    том же сбивают с толку.
- **Штраф за непереданный трек — 150% его «стоимости»** (`PENALTY_RATE`,
  правка 17.09.2026): аванс / количество треков × 1.5, округление до рубля.
  Было 100%, то есть ровно стоимость, — такой штраф нарушителю ничего не
  стоит: не передал трек, вернул полученное за него. Считается в двух местах
  (`resolve_penalty_raw` и `computePenalty` в форме — живой пересчёт), и
  коэффициент в обоих назван одинаково, чтобы правка не потерялась в одном
  из них. Вписанная руками сумма, как и раньше, не пересчитывается.

- **Количество треков прописью — В РОДИТЕЛЬНОМ ПАДЕЖЕ** (`build_count_text`,
  правка 17.09.2026): «не менее 5 (пяти) Треков», а не «5 (пять)». Метки
  `count_text` и `count_middle_text` во всех пяти шаблонах, где встречаются,
  стоят в обороте «не менее N (…) Треков/Объектов», а он требует родительного.
  Родительные числительные в проекте уже были — для «в течение 10 (десяти)
  рабочих дней»; расширены до 999, потому что обязательство на полторы сотни
  позиций бывает, а на полторы тысячи — нет.
- **ВЁРСТКА ДОГОВОРОВ «АВАНС + ОБЯЗАТЕЛЬСТВО» ПРИВЕДЕНА К «Договор_СГ_аванс»**
  (17.09.2026, просьба владельца). Эталон — именно он, и различия были видны
  глазами:
  - **«Приложение № 1» начинается с новой страницы.** В эталоне оно открывает
    отдельный раздел, а в этих двух договорах стояло посреди раздела, сразу за
    подписями, и съезжало вместе с текстом выше. Поставлен разрыв страницы
    перед заголовком (`pageBreakBefore`) — тот же результат, что у раздела, но
    без перекройки структуры документа. Так же, кстати, сделан «АКТ
    ПРИЁМА-ПЕРЕДАЧИ» в самом эталоне.
  - **Места для подписи в нижнем колонтитуле — НЕ ВЕЗДЕ.** Роль раздела решает:
    тело договора и Финансовое соглашение — с подписями, страницы Приложения —
    только номер страницы. Колонтитулы скопированы из эталона по этим ролям, а
    не подогнаны руками, чтобы не разойтись в мелочах.
  - **Из шапки убрано лишнее «МЛ-»**: номер договора уже начинается с «МЛ-»
    (`build_contract_number`, и в базе 188 из 258 номеров такие), а в
    колонтитуле стояло «№ МЛ-{{ contract }}» — выходило «№ МЛ-МЛ-17/09/26-…».
    **В остальных шаблонах это не исправлено** — в том же «Договор_СГ_аванс»
    удвоение есть, и правку лучше делать разом и осознанно.
- **Шаблоны на проде уже правлены** (залиты 17.09.2026 поверх прежних,
  `maps_to` сохранён, version +1). Word-исходники владельца лежат рядом с
  проектом в «Формы договоров» — там же копии с суффиксом «(пункты аванса
  условные)». Правя шаблон в Word заново, эти условия легко потерять: они
  выглядят как обычный текст `{%p if clause_first %}` в отдельном абзаце.

**Над формой генерации бывает КРАСНОЕ ПРЕДУПРЕЖДЕНИЕ, и его текст приходит с
сервера** (`notice` в ответе `GET /templates/{id}/fields`, 17.09.2026). Сейчас
оно висит у четырёх договоров «с обязательством» (СГ и ИП × аванс и роялти):
их ещё не смотрел юрист, и готовый документ надо вычитать перед отправкой.
- **Список — СЕМЕЙСТВАМИ договоров** (`UNAPPROVED_CONTRACT_FAMILIES` в
  `tags.py`), а не id шаблонов: id на каждом стенде свои, а семейство — то же
  самое. Приложения и акты не входят: у них ось другая (бакет обязательства),
  и они давно в работе.
- **Решает сервер, а не фронт.** Какие шаблоны юрист не смотрел — знание про
  документы, и лежит оно рядом с остальными правилами по договорам. Форма
  просто рисует красным то, что пришло; одобрят договоры — удаляется одна
  строка, фронт не трогаем.
- Отдельного поля «одобрено» в базе НЕТ намеренно: это состояние на неделю-две,
  а колонка плюс тумблер в модалке — навсегда. Понадобится снимать плашку по
  одному шаблону — тогда и заводить.

**Форма генерации разбита на разделы «Документ», «Аванс», «Обязательство»**
(17.09.2026, просьба владельца: «визуально перегружено»). В договоре с авансом
и обязательством раздел «Документ» собирал двенадцать полей подряд — дата,
ставки, четыре суммы аванса, сроки, штраф, — и глазу было не за что зацепиться.
Разделы повторяют структуру самого договора: условия документа, порядок
выплаты, обязательство по трекам. Механизм прежний — группа поля в `FIELD_META`
плюс `GROUP_ORDER`, никаких новых сущностей; у договоров без аванса разделы
просто не появляются. Подписи частей аванса при этом укоротились («До сдачи
треков» вместо «Аванс: до сдачи треков»): слово «Аванс» говорит заголовок.

**В модалке настройки шаблона поля из карточки контрагента — НАВЕРХУ списка**
(17.09.2026, просьба владельца). Порядок: сначала уже связанные
(`maps_to ≠ manual`), потом те, что обычно связывают (`CARD_FIELD_HINTS` в
`tags.py`, приходят в `/templates/maps-to-options`), потом всё остальное;
внутри групп порядок прежний — сортировка устойчивая. Настраивают всегда одни и
те же метки (ФИО, рег. номер, роялти, номер договора, псевдоним), а лежали они
вперемешку с тремя десятками обычных полей. На саму подстановку это не влияет:
источник по-прежнему назначает админ руками.

**Готовые документы нигде не хранятся.** `POST /templates/{id}/generate` рендерит
docx/pdf "на лету" и не кладёт результат ни в MinIO, ни куда-либо ещё (было
осознанное решение ещё на этапе 6 — см. `models.py`: раньше там был явный
комментарий "generated_documents сознательно НЕТ"). На этапе 7 это решение
пересмотрено под конкретную задачу — вкладку "История генерации": вместо файла
таблица `generated_documents` хранит payload формы + template_id, и результат
можно воссоздать по требованию тем же `render_document()`. Если шаблон с
момента генерации перезалили — воссозданный документ будет соответствовать
НОВОЙ версии шаблона, это ожидаемый компромисс (см. докстринг `GeneratedDocument`).

## Как всё устроено (то, что неочевидно из кода)

- **JWT**: access 30 мин, refresh 14 дней с ротацией при каждом использовании.
  В `client.js` есть замок на refresh — несколько параллельных 401 не должны дёргать
  `/auth/refresh` каждый своим токеном, иначе второй придёт с уже отозванным и
  выкинет на логин при живой сессии.
- **Тема**: light по умолчанию, ручное переключение, хранится в localStorage `ml_theme`.
- **У каждой вкладки СВОЯ ШАПКА — название и одна строка о том, что это за
  экран** (`components/ui/PageHeader.jsx`, 17.09.2026). Раньше шапка была
  написана руками только в «Номенклатуре» и «Партнёрах», а остальные вкладки
  начинались прямо с карточки поиска — и человек, переходя между ними, то
  видел, куда попал, то нет. Теперь размеры и отступы живут в одном месте.
  - **Описание — ОДНА фраза** про то, что здесь можно сделать, а не пересказ
    интерфейса: длинный текст над каждым экраном перестают читать на третьем.
    Исключение — «Dista Connect»: там человек грузит файл, меняющий базу, и
    порядок действий держится перед глазами.
  - **У «Генерации» шапки НЕТ** (решение владельца 17.09.2026): у неё свой
    крупный экран с приглашением найти контрагента, и служебная строчка над
    ним только мешала бы. Формы генерации это тоже не касается — она вообще
    не вкладка.
  - `spaced={false}` — там, где расстояние уже задаёт контейнер (`gap-6` у
    «Кубка» и «Уведомлений») или `mt-6` у следующей карточки: иначе отступ
    выходит двойным.
- **Модалки**: стек, Escape закрывает только верхнюю (`isTop` из `ModalRoot`).
  **ФОКУС ПЕРЕЕЗЖАЕТ В ОКНО ПРИ ОТКРЫТИИ** (правка 24.09.2026, замечание
  владельца). Окно открывают кнопкой, и фокус оставался на ней: Enter в
  открытом окне подтверждения снова жал мусорку в строке и открывал ВТОРОЕ
  такое же окно поверх первого. Ловушка общая для любого окна, открытого
  кнопкой, поэтому чинится в `Modal`, а не в конкретной модалке.
  - **Только если фокус СНАРУЖИ**: окно с полем ввода наводит фокус само
    (`autoFocus`), и перетягивать его на рамку значило бы ломать ввод.
    Наш эффект отрабатывает после `autoFocus` детей, так что проверка
    «фокус уже внутри» честная.
  - Рамке окна дан `tabIndex={-1}`: годная цель для фокуса, но не участвует
    в обходе по Tab — это не элемент управления. Обводка снята
    (`outline-none`), иначе окно обрисовывалось бы системной рамкой.
  - **У `ConfirmModal` фокус сразу на кнопке действия**, а не на рамке: окно
    состоит из одного вопроса, и ответ на него — Enter. Escape отменяет.
    Остальные окна забирают фокус на рамку — там Enter не должен ничего
    решать за человека.
  **Правка и удаление — ЗНАЧКАМИ В ШАПКЕ, рядом с крестиком** (17.09.2026,
  решение владельца): `Modal` принимает `actions`, а сами кнопки — компонент
  `ModalAction` (карандаш ✎ и мусорка 🗑, круглые и того же размера, что
  крестик). Раньше они стояли внизу вперемешку с действиями «дальше»
  («Документы», «Внести поступление») и читались как продолжение сценария, а
  править и удалять — это про сам объект, а не следующий шаг. Внизу осталось
  только то, ради чего окно открывают дальше.
  - **Подтверждение удаления осталось ВНИЗУ**, хотя кнопка уехала вверх:
    вопрос «удалить безвозвратно?» требует ответа, и прятать его в ряд
    значков — самый верный способ получить случайное «да».
  - У значка обязателен `title`: значок без подписи — загадка, и наведение
    мышью единственный способ её разгадать (оно же уходит в `aria-label`).
    Красным красится только удаление, иначе ряд превращается в светофор.
  - **Значки РИСОВАННЫЕ (`components/ui/icons.jsx`), а не эмодзи.** Сначала
    стояли ✎ и 🗑; увеличение размера и веса не помогло — эмодзи рисует
    системный шрифт, он приходит со своим цветом и своими пропорциями и не
    слушается ни `color`, ни толком `font-size`: на Windows мусорка выходила
    мелким красным пятном. SVG берёт цвет кнопки через `currentColor`,
    поэтому красный у удаления и приглушённый у выключенной получаются сами,
    а общая толщина линии держит ряд единым набором.
  - **Карточку контрагента в ML Finance теперь тоже можно править и
    удалять** (17.09.2026): те же значки, та же модалка правки, что в ML
    Docs — набор полей и права живут там, и заводить финансам свою форму
    значило бы держать две правды об одной карточке. Удаление упирается в те
    же 409: операции и права в номенклатуре.
  **Кнопка «назад» в браузере закрывает модалку, а не уносит со страницы**
  (17.09.2026). Раньше модалка жила вне истории: открыв карточку трека и
  нажав «назад», человек уезжал на предыдущую вкладку, а карточка оставалась
  висеть поверх неё. Теперь открытие кладёт в историю ОДНУ запись с ТЕМ ЖЕ
  адресом, `popstate` снимает верхнюю модалку, а закрытие крестиком делает
  `history.back()` — иначе в истории копились бы пустышки и «назад» после
  крестика не делал бы ничего видимого. Неочевидное:
  - **Адрес не меняется намеренно.** Модалка не экран: ссылку на неё не
    пересылают, и, попади она в URL, её пришлось бы уметь восстанавливать
    при открытии по ссылке — вместе со всем, что в неё передали пропсами.
  - **Счётчики живут в отдельном модуле** `modals/modalHistory.js`, а не
    внутри провайдера: ошибка в них проявляется не сразу, а на второй-третьей
    модалке, и проверять их удобнее без React (в scratchpad лежит
    `test_modal_history.mjs` с поддельной историей браузера — восемь
    сценариев, включая вложенные модалки и выход из формы).
  - **Свой же `back()` узнаётся по счётчику** `selfBack`, иначе закрытие
    крестиком закрыло бы заодно и модалку под ним.
  - **`closeAllModals` историю НЕ отматывает.** Его зовут ровно перед уходом
    на другой экран (`ContragentDocsModal` → форма генерации), а браузер
    выполняет `back()` отложенно: он сработал бы уже ПОСЛЕ перехода и утащил
    бы человека обратно. Оставшаяся запись безобидна — у неё тот же адрес,
    что у экрана, с которого ушли.
  - **Кто уходит со страницы относительной навигацией при открытой модалке,
    обязан перешагнуть её запись**: `navigate(-(1 + modalHistory.depth))`.
    Так сделан выход из формы генерации; две уходящие кнопки в
    `ConfirmExitDraftModal` поэтому НЕ зовут `closeModal` — модалку закроет
    `popstate` от самого перехода, а закрытие добавило бы второй прыжок по
    истории, и человек уехал бы на страницу дальше, чем собирался.
- **Никнеймы**: у контрагента их может быть несколько. Если `maps_to='contragent.nickname'`,
  сервер шлёт `nickname_options` (список) вместо одного default'а — фронт рисует select.
- **Парный Акт**: у Приложения, открытого по контрагенту, ищется Акт той же связки тегов
  и предлагается сформировать по тем же данным.
- **Шрифты в конвертере PDF — условие работоспособности, а не мелочь.** Договоры
  свёрстаны целиком в Times New Roman; если его нет в контейнере, LibreOffice МОЛЧА
  подменяет шрифт, метрики едут и PDF перестаёт совпадать с .docx (строки переносятся
  иначе, колонки таблиц пересчитываются). Так и было до 16.07.2026: `--no-install-recommends`
  вырезал `fonts-liberation` (он у libreoffice в Recommends), и `fc-match 'Times New Roman'`
  отдавал DejaVu Serif. Теперь в образе настоящий TNR (`ttf-mscorefonts-installer`) +
  Liberation вторым эшелоном. Проверка после правок конвертера:
  `docker compose exec converter fc-match 'Times New Roman'` → должен ответить TNR.
- **DejaVu Serif в PDF на колонтитулах — известно и принято** (17.07.2026). Колонтитулы
  шаблонов не задают шрифт явно и берут его из темы документа, а тема — `Aptos` (новый
  дефолт Microsoft вместо Calibri). Aptos в контейнере нет и не будет (лицензируется с
  Microsoft 365), поэтому LibreOffice роняет его в DejaVu Serif: в Word строка колонтитула
  сансерифная, в PDF — с засечками. Тело документа и таблицы при этом совпадают точно.
  Решено оставить как есть — не считать багом. Если однажды понадобится идеальное
  совпадение, дешёвый путь — прописать TNR в колонтитуле самого шаблона.
- **Конвертер НЕ смонтирован volume'ом** (в отличие от `backend/app`): push его не
  обновляет. После правок `converter/` — пересборка образа на сервере:
  `docker compose build converter && docker compose up -d converter`.
- **Тип договора — это ДВЕ оси, а не одна** (решение 03.08.2026, см. `app/tags.py`).
  `contract_family` слит из платёжной оси (АВАНС/РОЯЛТИ) и оси обязательства
  (без/с). Поэтому **договоров 4** (платёж × обязательство): АВАНС, РОЯЛТИ,
  АВАНС_ОБЯЗАТЕЛЬСТВО, РОЯЛТИ_ОБЯЗАТЕЛЬСТВО. А **приложения и акты различаются
  ТОЛЬКО по обязательству** — их 2 вида каждого: акт роялти = акт аванс,
  приложение аванс+обяз = приложение роялти+обяз. Поэтому приложение/акт
  тегируются НЕ семейством, а **бакетом обязательства** (`OBLIGATION_BUCKETS`:
  `БЕЗ_ОБЯЗАТЕЛЬСТВА` / `ОБЯЗАТЕЛЬСТВО`), не смешивая с 4 семействами. Договор
  РОЯЛТИ_ОБЯЗАТЕЛЬСТВО можно завести без своего приложения — оно общее с
  аванс+обяз. Схема не меняется: `contract_family` — varchar, бакеты просто
  другие значения в той же колонке, разделённые по `doc_type`.
- **Подбор документов** контрагенту — по country/contragent_type, а тип
  договора (contract_family) **условный** и работает ПО-РАЗНОМУ по `doc_type`:
  задан у карточки → договор сужается до точного семейства, а приложение/акт —
  до **бакета** (семейство контрагента сворачивается в бакет функцией
  `obligation_bucket()`, суффикс `_ОБЯЗАТЕЛЬСТВО`); пуст → показываем всё
  (все 4 семейства договоров и оба бакета), оператор выбирает (по просьбе
  владельца). Несовпадение регистра/значения тегов = документ просто не найдётся,
  без ошибки — помнить при отладке. Парный Акт у Приложения: у обоих ОДИН И ТОТ ЖЕ
  бакет, поэтому фронт сравнивает их `contract_family` напрямую (DocFormPage) —
  просто теперь это бакет. contract_family карточки **не входит в подсветку
  неполноты** (`_contragent_is_complete`): пустой тип договора не повод красить
  карточку.
- **Тег приложения/акта валидируется по `doc_type`** (`normalize_contract_family_for`
  в `app/tags.py`): для appendix/act допустимы только бакеты, для договора —
  семейства. Модалка шаблона (`New/EditTemplateModal`) показывает нужный
  справочник в зависимости от типа документа; `/tags` отдаёт `obligation_buckets`.
- **Списки в форме**: пустые строки отбрасываются при сборке payload, но галочки
  (`has_profanity`, `is_group`) при проверке «строка пустая?» не учитываются — иначе
  строка с одной галочкой попала бы в документ пустой.
- **Журнал действий показывает только работу людей** (10.09.2026). `log_action`
  вызывается из функций-роутеров, а их же дёргают E2E- и отладочные скрипты
  внутри контейнера — и их правки ложились в `audit_log` неотличимо от работы
  человека. Масштаб на момент правки: **69 записей из 241 (29%)** — прогоны
  тестов; в частности, за учёткой менеджера German числились две «правки
  карточек» в дни, когда он в сервис не входил вообще. Теперь ASGI-мидлварь
  (`app/request_context.py`) поднимает флаг на время HTTP-запроса, а
  `log_action` при опущенном флаге ставит `meta.via='script'`; `GET /audit-log`
  такие записи прячет (`?include_script=true` — показать все). Неочевидное:
  - **Запись создаётся всегда, даже помеченная.** Если определение источника
    однажды собьётся, в журнале появится лишняя строка, а не бесследно
    исчезнет настоящая — для журнала это несопоставимо меньшая беда.
  - **Фильтр через `IS DISTINCT FROM`, а не `!=`:** у записи без метки
    `meta->>'via'` равен NULL, а `NULL != 'script'` даёт NULL — обычное
    сравнение выбросило бы из выдачи ровно те строки, ради которых написано.
  - **Мидлварь именно «чистая» ASGI, а не `@app.middleware("http")`:**
    `BaseHTTPMiddleware` исполняет приложение в отдельной задаче, и ContextVar
    вокруг вызова ведёт себя непредсказуемо. Синхронные эндпоинты FastAPI
    уносит в пул потоков с КОПИЕЙ контекста — флаг в копию попадает.
  - Исторические 69 записей помечены задним числом (не удалены), разметка
    сделана сверкой каждой записи с HTTP-логом контейнера: нет запроса в ту
    секунду — значит, скрипт. Это разовая археология, повторить её на новых
    данных не получится (docker-лог не вечен).
  - **Журнал нигде не показывается в интерфейсе** — ни в React, ни в старом
    `index.html`; он доступен только через API (`GET /audit-log`, admin/director).

      нельзя. Но политика строже: **строка, которую не разобрали, роняет
      загрузку целиком**. В номенклатуре кривую строку можно пропустить, а
      здесь это деньги площадки — «частично загружено» хуже отказа.
    - **Строки сопоставляются с каталогом по артикулу** при загрузке, и
      неопознанные считаются (`unmatched_count`). Это не ошибка загрузки, а
      работа на потом: по такой строке деньги пришли, а делить их не на что.
    - **ЧТО НЕ НАШЛОСЬ — УХОДИТ В ПОЗИЦИЮ «ВНЕ КАТАЛОГА»** (`OUTSIDE_SKU =
      "0000001"`, просьба владельца 24.09.2026). Раньше такая строка лежала
      совсем без ссылки на трек, и выгрузить по ней что-либо было нельзя:
      «деньги пришли, а на что — неизвестно» жило только числом в списке
      отчётов. Теперь у них общий адрес, и в конце квартала по нему видно всё
      разом.
      - **АРТИКУЛ СТРОКИ НЕ ЗАТИРАЕТСЯ** (уточнение владельца): в новом
        квартале код может стать рабочим, если номенклатуру поправят.
        Меняется только `track_id`; в `sku` остаётся то, что прислала
        площадка. Перезалили отчёт после правки каталога — строка привяжется
        к настоящему треку сама.
      - **Это настоящая строка в `tracks`**, а не признак у строки отчёта:
        так она ведёт себя как любой другой трек — по ней работает и
        выгрузка, и будущий расчёт, и ничего не надо учить исключению.
        Заводится при первой надобности (`outside_track_id`), а не
        миграцией: позиция служебная, и на стенде, где отчёты ещё не грузили,
        ей взяться неоткуда.
      - **ПРАВ У НЕЁ НЕТ И БЫТЬ НЕ ДОЛЖНО**: эти деньги пока ничьи, и
        придумать им владельца значит отдать не тому.
      - **Разнесённой такая строка НЕ считается**: `unmatched_count` и
        `unmatched_amount` считаются ДО привязки, фильтр «не опознано»
        показывает и приёмник тоже, а в выдаче строк `matched` у неё false.
        Иначе сигнал «деньги ничьи» исчез бы ровно в тот момент, когда его
        сделали удобнее смотреть.
      - **Следующая выгрузка Dista её не тронет**: импорт правит только
        артикулы из файла, а архивирование исчезнувших идёт лишь по явному
        `--archive-missing` — с ним позицию отправит в архив, и это надо
        помнить.
    - **СТРОКЕ БЕЗ АРТИКУЛА АРТИКУЛ ПОДБИРАЕТСЯ ПО НАЗВАНИЮ И ИСПОЛНИТЕЛЮ**
      (просьба владельца 18.09.2026, `pick_track` в `partner_reports.py`,
      `_resolve_tracks` в роутере). У площадки код объекта проставлен не
      всегда: в отчёте МТС таких строк шесть, и все шесть на самом деле есть в
      каталоге — просто исполнитель записан иначе («ПОШЛАЯ МОЛЛИ» против
      «Пошлая Молли», «Slim & Константа» против «Slim, Константа»).
      - **Только сильное совпадение.** Название сходится ЦЕЛИКОМ с точностью
        до регистра, «ё» и знаков препинания («Тмстс!» = «тмстс»); исполнитель
        сравнивается НАБОРАМИ СЛОВ, по слову на слово, с поправкой на
        разделители, служебные «feat/ft/prod» и сокращение до инициала
        («Ю. Шатунов» = «Юрий Шатунов»). Подошло больше одного трека — не
        берём НИ ОДНОГО: угаданный артикул хуже пустого, потому что деньги
        уедут молча и не туда.
      - **Почему сравнение наборов, а не вхождение**: «ОСОБОВ» содержится в
        «ОСОБОВ feat. TRUEтень», но это разные записи. Настоящий случай —
        «Азимут»: в каталоге их пять, и у двух почти одинаковый состав
        («Slim, Константа» и «SLIMUS, Константа»); по вхождению деньги уехали
        бы не тому.
      - **Кандидатов ищем по самому длинному слову названия** (`ilike '%…%'`,
        лимит 200), а не по названию целиком: точное сравнение промахнулось бы
        на знаке вопроса, а полнотекстового поиска здесь не нужно — решает
        всё равно строгая проверка. Пары «название + исполнитель»
        кешируются: в отчёте они повторяются по нескольку строк.
      - **Подбор виден человеку**: в предпросмотре у такой строки пометка
        «подобран», после загрузки — «артикулов подобрано по названию: N».
        Подбор — догадка сервиса, пусть и строгая, и выдавать её за данные
        площадки нельзя.
      - **Исполнитель поэтому хранится в строке отчёта** (`artist`, миграция
        `e9c47b31d8a5`): он же отвечает на вопрос «а что это за трек» в
        списке неразнесённых — одного названия для этого мало.
    - **КОД ПЛОЩАДКИ — ОТДЕЛЬНОЕ ПОЛЕ ПРАВИЛА, а не «Артикул»** (`code`,
      замечание владельца 24.09.2026). Сутки колонка «UPC / ISRC» у «101 и К»
      подставлялась в «Артикул», и поле врало: в нём стоял чужой код, а в
      строку уезжал НАШ артикул, найденный по этому коду. Человек видел в
      настройке одно, а в предпросмотре другое.
      - **«ЗАПОЛНЯЕТСЯ ПРАВИЛОМ» — ОТДЕЛЬНЫЙ ПУНКТ СПИСКА, а не пустота**
        (`{"auto": true}`, уточнение владельца 24.09.2026). Сутки это была
        пустая строка выбора, и вышло хуже исходного: прочерк должен значить
        ровно «артикул ниоткуда не берётся», то есть ошибку настройки. **Код
        площадки указан верно не всегда**, поэтому артикул ОБЯЗАТЕЛЕН
        (`sku_configured`), и правило без него сервер не принимает.
        Выбравший этот пункт получает артикул по коду площадки, по названию с
        исполнителем или руками в предпросмотре — и тогда сопоставление
        запоминается для площадки (`partner_track_aliases`).
      - **Колонка кода в настройке НЕ показывается**: человеку важно одно —
        берётся артикул из файла или находится. Сама колонка живёт в правиле
        площадки (`BUILTIN_RULES`), там ей и место: это свойство формата, а
        не решение оператора.
      - **ГРАБЛЯ: сохранённое правило партнёра сильнее встроенного.** У «101
        и К» от первой загрузки осталась копия со старым `sku` → «UPC /
        ISRC», и экран показывал её, сколько бы ни правили код. Копию
        удалили; при правке `BUILTIN_RULES` проверять
        `partner_report_rules` — иначе правка не видна.
      - **Догадка по названиям колонок** отправляет «isrc» и «upc» в код, а
        не в артикул.
      - **Строка мусора отсекается по обоим полям** (`not sku and not code`):
        у площадки без колонки артикула иначе каждая строка проверялась бы
        на «Итого».
    - **ТРЕК ИЩЕТСЯ ПО ISRC, когда нашего артикула в отчёте нет вовсе**
      (`_code_candidates` / `_tracks_by_code`, 24.09.2026). У «101 и К»
      колонка одна и называется «UPC / ISRC», а внутри оба кода через косую:
      «3617380567893 / DG-A0P-23-16666». Режем по черте, с каждого куска
      снимаем знаки («DGA0P2316666») и ищем в `tracks.code`.
      - **Неоднозначный код не берём вовсе**: один ISRC в каталоге бывает у
        семнадцати позиций (одна запись в разных альбомах), и выбрать из них
        наугад значит отправить деньги не туда. Такая строка остаётся
        неразнесённой, а артикул ей впишет человек.
      - **Куски короче восьми знаков отбрасываем**: «1» или «н/д» кодом быть
        не может, а совпасть случайно — вполне.
      - **Порядок привязки стал такой**: артикул из файла → запомненное
        сопоставление → КОД (ISRC/UPC) → подбор по названию. Код ниже
        запомненного: там решение человека, а здесь опознание по коду.
      - **Артикул в строке подменяется на НАШ**: строка уезжает в базу, и
        хранить в ней чужой код значило бы искать трек ещё раз.
      - На образце «101 и К» так находятся три трека из четырёх; четвёртый
        («Ёлка — Понедельник») приехал без кода вовсе и нашёлся подбором по
        названию.
    - **АРТИКУЛ МОЖНО ВПИСАТЬ РУКАМИ ПРЯМО В ПРЕДПРОСМОТРЕ** (просьба
      владельца 18.09.2026): у строки без найденного трека вместо текста поле
      ввода, рядом сервис отвечает, что это за трек (`GET
      /partner-reports/track?sku=`) — код из соседней системы сам по себе не
      подтверждает, что трек тот же. Вписанное уезжает формой `manual_skus`
      ({номер строки: артикул}) и применяется ДО привязки к каталогу, в
      предпросмотре и при загрузке одинаково. Нужно это там, где подбор по
      названию честно отказался: «Азимут» в каталоге лежит пятью треками, и
      выбрать из них может только человек.
      - **В правило партнёра это не попадает**: правило — про формат файла,
        а вписанный код относится к одной строке одного отчёта.
      - **Номера строк привязаны к файлу**: выбрали другой файл — вписанное
        сбрасывается, иначе код достался бы чужой строке.
    - **ВПИСАННЫЙ АРТИКУЛ ЗАПОМИНАЕТСЯ ДЛЯ ПЛОЩАДКИ** (`partner_track_aliases`,
      просьба владельца 18.09.2026): в следующем её отчёте тот же трек приедет
      уже с артикулом. Отчёты приходят регулярно, позиции в них повторяются, и
      решать одну и ту же задачу каждый месяц человек не должен.
      - **Ключ — ПЛОЩАДКА + НАЗВАНИЕ + ИСПОЛНИТЕЛЬ.** Одного названия мало (в
        каталоге пять «Азимутов»), а площадка в ключе потому, что пишут
        названия все по-своему: «ПОШЛАЯ МОЛЛИ» у одной и «Пошлая Молли» у
        другой. Ключи хранятся нормализованными ТЕМ ЖЕ кодом, что и подбор по
        названию, — иначе «Тмстс!» и «тмстс» стали бы разными ключами.
      - **Порядок привязки**: артикул из файла → запомненное сопоставление →
        подбор по названию. Решение человека сильнее догадки сервиса, поэтому
        оно выше подбора; и оно же выигрывает у кода, которого нет в каталоге.
      - **Запоминаем только то, что нашлось в каталоге**: код с опечаткой,
        которому ничего не соответствует, повторять из месяца в месяц незачем.
        Вписали другой артикул той же строке — верим последнему решению.
      - **Хранится АРТИКУЛ, а не ссылка на трек**: артикул — наш код и
        переживает перезаливку каталога, а id трека при ней меняется.
      - **Список видно и можно убрать** («Запомненные артикулы этой площадки»
        под загрузкой файла, `GET|DELETE /partner-reports/aliases/…`).
        Сопоставление, сделанное по ошибке, иначе повторялось бы в каждом
        следующем отчёте молча. Рядом подписано, что это за трек СЕЙЧАС, —
        каталог живёт своей жизнью, и позиции может уже не быть.
    - **КОЛИЧЕСТВО В ПРЕДПРОСМОТРЕ — СЧЁТ, А НЕ ДЕНЬГИ** (замечание владельца
      24.09.2026): «493 817», а не «493817.00». Сервер отдаёт его строкой с
      двумя знаками, как и суммы (колонка `Numeric(16,2)`), но хвост «,00» у
      прослушиваний читается как машинный вид. Дробное сохраняем: у части
      площадок количество приходит долями.
    - **ПРЕДПРОСМОТР РАЗБИРАЕТ ВЕСЬ ФАЙЛ**, а показывает начало (5 строк, без
      прокрутки — правки 18.09.2026: предпросмотр отвечает на один вопрос,
      верно ли поняты колонки, и пяти строк для этого хватает) и — ОТДЕЛЬНЫМ
      СПИСКОМ, по кнопке —
      строки без трека (до 300). Правка 18.09.2026: раньше разбиралась первая
      сотня строк, и кнопка «показать строки без артикула» показала бы не
      строки без артикула, а те из них, что случайно попали в начало (в отчёте
      МТС они лежат на 468-й и 577-й). Списка ДВА, а не один склеенный:
      дописанные в конец таблицы, эти строки выглядели так, будто отчёт ими
      заканчивается. В интерфейсе они называются «строки, которых нет в
      номенклатуре», а не «без артикула»: код в отчёте может стоять, а трека с
      таким кодом у нас не быть — и работа с такой строкой ровно та же.
    - **НАСТРОЙКА КОЛОНОК СПРЯТАНА, когда правило известно** (правка
      18.09.2026, просьба владельца). Шесть полей с уже подставленными
      значениями — готовый ответ, который человек не правит, а место занимает
      до самого главного: предпросмотра. Открывается ссылкой «настроить
      колонки» и показывается сама, если правила нет (`rule_source ===
      'guess'`) — там колонки как раз надо проверить. Кнопка «Применить и
      пересобрать» живёт ВНУТРИ настройки: файл разбирается заново с новым
      правилом, и делать это на каждую правку поля незачем.
    - **ГОТОВАЯ ФОРМУЛА ПОКАЗАНА СЛОВАМИ «Рассчитано по формуле»**, а не
      выражением (правка 18.09.2026): у площадок названия колонок длиной в
      предложение, и формула в поле всё равно не помещается — читается как
      мусор. Само выражение — в подсказке при наведении и по ссылке
      «изменить». Тогда же убраны показ первых строк файла и значения колонок
      в списках выбора: правило теперь приезжает готовым, а не пишется
      руками, и обе подпорки только загромождали экран.
    - **ПОДОБРАННЫЙ АРТИКУЛ ПОКАЗАН КАК ОБЫЧНЫЙ** (правка 18.09.2026, решение
      владельца: «если треки подобраны, считаем это за истину и не
      акцентируем внимание»). Пометки «подобран»/«вписан» в таблице и строка
      «из них подобрано по названию: N» убраны: подбор строгий, перепроверять
      его человек всё равно не будет, а пометка требует внимания к тому, с чем
      делать нечего. Осталось ОДНО число — сколько строк не привязалось к
      номенклатуре («Нет в номенклатуре: N строк»). Оно же честнее прежних
      двух: «без артикула» считалось уже ПОСЛЕ подбора и выглядело нелепо
      («без артикула: 1 строк, из них подобрано 4»).
    - **Партнёр выбирается ПОИСКОМ** (`PartnerPicker`), а не списком: площадок
      больше сотни, и список, который надо листать до нужной буквы, — ровно
      та работа, от которой поиск избавляет. Ищет по имени и по коду Dista,
      список сужается с первой буквы.
    - **Удаление спрашивает СВОИМ окном** (`ConfirmDeleteReportModal`, правка
      18.09.2026): решение принимают, глядя на сам отчёт — чья площадка, за
      какой период и на какую сумму, — а браузерный `confirm` умеет показать
      одну строку текста и не подчиняется общим правилам стека модалок
      (Escape, кнопка «назад», затемнение). Окно и удаляет само, как карточка
      партнёра: иначе «удаляем…» и текст ошибки пришлось бы держать ещё и на
      странице.
    - **ОТЧЁТ ПРИВЯЗЫВАЕТСЯ К СТРОКЕ ПОСТУПЛЕНИЯ** (19.09.2026, просьба
      владельца): нажатие на строку в списке загруженных открывает окно «к
      какому поступлению относится этот отчёт» — сначала квартал, потом
      строка из таблицы поступлений за него.
      - **Сначала квартал, а не подставляем период отчёта**: платят позже
        отчётного периода — за второй квартал в третьем.
      - **«Сумма фактического завода» у поступления СЧИТАЕТСЯ** как сумма
        привязанных к нему отчётов (`_sync_payment_actual`), а не вводится
        руками: числа уже в базе. Пока привязан хоть один отчёт, поле НЕ
        ПРАВИТСЯ — ни на экране (вместо поля текст со стрелкой ↩ и
        подсказкой), ни через API (409): правка всё равно затёрлась бы при
        следующей привязке. Отвязали все отчёты — поле снова обычное. Одним платежом закрывают несколько
        отчётов — поэтому сумма, а не итог последнего. Отвязали последний —
        поле очищается, иначе в таблице висело бы число, которому нечем
        объясниться.
      - **ПОДХОДЯЩАЯ СТРОКА ПОКАЗЫВАЕТСЯ ПЕРВОЙ** (просьба владельца
        24.09.2026: «совпадение очевидное, не нужно тратить время, чтобы
        найти его в общем списке»). Признак — площадка та же и СУММА ЗАВОДА
        равна итогу отчёта. Строка уезжает наверх, подсвечивается и
        подписывается, ПОЧЕМУ она там: подсказка, за которой не видно
        основания, — это гадание, а человек отвечает за то, к чему привязал
        деньги.
        - **Сверяется сумма завода, а не поступления**: привязка нужна
          затем, чтобы завод сошёлся с фактическим заводом, и итог отчёта
          сравнивают именно с ним. Сумма поступления — то, что упало на
          счёт, вместе с чужими деньгами и до всех пересчётов.

      как это разбирается:

        нашлись в каталоге буква в букву;

        две ставки, а авторские и смежные считаются формулой
        `[Сумма…] * [Ставка…авторские] / ([Ставка…авторские] + [Ставка…смежные])`.
        Сверено с колонками «авт»/«смж», которые владелец считал руками: 664
        строки, расхождений ноль, итог 40 916.36 и 81 902.40;

        «М.П.»). Итоговые узнаются по словам, подпись — по общему правилу
        «строка без единого числа не данные». Ноль при этом ДАННЫЕ: площадка
        честно сообщает, что денег не было;

        роняют файл, а артикул им подбирается по названию и исполнителю (см.
        выше) — все шесть нашлись в каталоге; что не нашлось бы, грузится
        неразнесённым.

    - **НАСТОЯЩИЕ ОТЧЁТЫ ОКАЗАЛИСЬ НА ДВА ПОРЯДКА КРУПНЕЕ МТС** (23.09.2026,
      разбор папки «Поступления 2кв 26» — 2.3 ГБ, 275 файлов, ~25 разных
      форматов). Весь механизм разбора был написан и проверен на единственном
      знакомом файле — МТС с его 657 строками, — и на боевых объёмах не
      работал вовсе. Замеры и правки:
      - **ТЕКСТОВЫЕ ОТЧЁТЫ ПРИХОДЯТ В cp1251, А НЕ В utf-8.** Believe,
        Spotify, ОМА, «Звук» — все. Прежний безусловный
        `decode("utf-8-sig", errors="replace")` превращал в «замену» каждый
        кириллический символ: до 70 тысяч штук на 200 КБ образца. Отчёт
        грузился БЕЗ ЕДИНОЙ ОШИБКИ и был негоден — мусором приезжали название
        и исполнитель, то есть ровно те поля, по которым подбирается артикул.
        Теперь кодировка определяется (`detect_encoding`): utf-8 строгой
        проверкой на первых 256 КБ, иначе cp1251. Порядок не переставлять —
        cp1251 принимает почти любой байт и потому годится только последним.
      - **`MAX_ROWS` был 300 000 и отсекал три четверти объёма** (Believe RU —
        584 тыс. строк, Spotify — 494 тыс., ОМА — 1.58 млн). Поднят до 3 млн.
        Прежняя оценка «квартальный отчёт это десятки тысяч строк» была снята
        с МТС и оказалась ошибкой на два порядка.
      - **ПРЕДЕЛ ПАРАМЕТРОВ В ЗАПРОСЕ — жёсткий отказ, а не медленность.**
        Привязка к каталогу собирала все артикулы в один `IN (...)`, а
        PostgreSQL принимает не больше 65 535 параметров: крупный отчёт не
        загружался ВООБЩЕ, сколько его ни жди. Теперь пачками по 10 000

      выписке, где каждый месяц лежит отдельным листом.
      - **ПОЧЕМУ НЕ ВЫЧИСЛЯЕМ.** Сутки номер считался порядком заведения
        (`created_at`) — и молча ломался: весь файл заводится ОДНИМ импортом,
        `created_at` у всех строк одинаковый, и порядок внутри месяца
        оставался на усмотрение запасного ключа сортировки (id). То есть
        номера были случайной перестановкой. А номером называют строку вслух,
        глядя в ту самую выписку, и на него ссылается вкладка «Отчёты».
      - **У строки, заведённой руками, номер ПЕРВЫЙ СВОБОДНЫЙ в её месяце**
        (`next_number`) и проставляется СРАЗУ, при записи: считай его при
        показе — он менялся бы от появления соседей. Свободный, а не
        «последний плюс один»: строки удаляют, и номер должен возвращаться в
        оборот, иначе нумерация месяца разойдётся с выпиской, где она
        сплошная.
      - **Переезд строки в ДРУГОЙ месяц номер переназначает** (в новом месяце
        принесённый наверняка занят), а правка даты внутри месяца — нет: им
        уже могли назвать строку.
      - **Номер из файла, который уже занят, уступает место свободному**:
        два импорта в один месяц не должны давать двух строк с одним номером.
      - `payment_numbers` остался и отдаёт готовые номера, а строкам без него
        раздаёт свободные вслед за занятыми — это строки, заведённые до
        появления колонки.
      - **Уже залитые 69 строк пронумерованы по тому же файлу** (24.09.2026),
        сверка по дате и сумме. Две июльские строки Believe по сумме не
        нашлись — владелец правил их руками после импорта, — и получили
        номера по дате и площадке.
    - **В СПИСКЕ ОТЧЁТОВ СТОЛБЕЦ «ПОСТУПЛЕНИЕ» ПОКАЗЫВАЕТ «№3 · МТС · 3 кв. 26»,
      А НЕ ДАТУ** (там же). Дата платежа ничего не говорит: отчётов за месяц
      несколько, платежи идут вперемешку, и «01.07.2026» повторяется у
      половины строк. Номер — то, чем человек называет строку вслух, а
      площадка и квартал позволяют узнать её, не открывая соседнюю вкладку.
      Подпись собирает СЕРВЕР (`_payment_label`), чтобы номер в двух местах
      считался одним кодом; дата осталась в подсказке при наведении.
    - **КОПЕЙКА В «РАСХОЖДЕНИИ» ЧИТАЕТСЯ КАК «СОШЛОСЬ»**
      (`_difference_matches`, тот же `TRANSFER_TOLERANCE`, 24.09.2026).
      Настоящий случай: у отчёта «101 и К» фактический завод 48 063,78, а
      сумма завода 48 063,79 — и ОБА ЧИСЛА ВЕРНЫ. Площадка считает с
      точностью до четвёртого знака, и в её файле стоит 58 637,8176
      (делится в 48 063,7849); банк двигает рубли с копейками, и в выписке
      58 637,82 (делится в 48 063,7869). Копейку создаёт не наше округление,
      а стык двух точностей, и красить её красным значит приучить не
      смотреть на этот столбец.
      - **Число не прячется**: оно по-прежнему в `difference` и показывается
        в подсказке к слову «сошлось» вместе с причиной.
      - **В ИТОГ ПОД ТАБЛИЦЕЙ такие копейки не идут**: иначе итог набирал бы
        по копейке со строк, про каждую из которых написано «сошлось», и
        противоречил бы сам себе.
      - **Чинить «правильным» округлением нельзя.** Считать итог отчёта как
        «округлённая сумма брутто / 1.22» дало бы искомые 48 063,79, но тогда
        сумма строк отчёта перестала бы сходиться с его итогом — а по этим
        строкам считают детализацию правообладателю. Расхождение в копейку
        между отчётом и выпиской честнее, чем отчёт, который не сходится сам
        с собой.
    - **СТОЛБЕЦ «РАСХОЖДЕНИЕ» = ЗАВОД − ФАКТИЧЕСКИЙ ЗАВОД** (просьба
      владельца 23.09.2026) — то, ради чего таблицу и ведут. Считает СЕРВЕР,
      как и итоги: суммы уходят строками, и вычитать их на экране нельзя.
      ПУСТО, пока не заполнены оба числа: разница с неизвестным — не находка,
      а шум, и «расхождение 116 300» у ещё не сверенной строки сбивало бы с
      толку. В итог под таблицей идут тоже только сверенные строки. Ноль
      пишется словом «сошлось»: «0,00» рядом с денежными колонками читается
      как «денег нет», а смысл ровно обратный.
    - **В ОКНЕ ПРИВЯЗКИ ОТЧЁТА ПОКАЗАНА СУММА ЗАВОДА, А НЕ СУММА ПОСТУПЛЕНИЯ**
      (уточнение владельца 23.09.2026). Привязка нужна ровно затем, чтобы
      ЗАВОД сошёлся с ФАКТИЧЕСКИМ ЗАВОДОМ, и сравнивать человек будет эти два
      числа. Сумма поступления к сверке отношения не имеет: это то, что упало
      на счёт — вместе с чужими деньгами и до всех пересчётов.
    - **ПУСТАЯ СУММА — НЕ НОЛЬ** (там же). Незаполненное значение рисовалось
      как «0,00 ₽»: `formatMoney(null)` приводит к нулю, и строка выглядела
      платежом на нулевую сумму, хотя число просто ещё не занесли — строку
      заводят по дате из выписки, а суммы дозаполняют позже, в этом весь смысл
      живого листа. Теперь пишем «завод не указан». Сам `formatMoney` не
      трогаем: в итогах ноль — это настоящий ноль.
    - **Квартал сверху, месяцы вкладками**: квартал — единица, которой
      считают отчёты, месяц — то, в чём лежит выписка. Отдельного поля
      «период» у строки нет, месяц и квартал — это отбор по дате
      поступления (так же сделан фильтр у отчётов).
    - **Обязательна только дата.** Строку начинают с выписки, а чей платёж и
      на какую сумму — дозаполняют следом; партнёр поэтому nullable. Новая
      строка заводится ПЕРВЫМ ЧИСЛОМ открытого месяца, а не сегодняшним
      днём: иначе в июльской таблице она появилась бы с декабрьской датой и
      пропала из виду.
    - **Площадка выбирается ПОИСКОМ** (`components/ui/PartnerPicker`): их
      больше сотни, и листать список до нужной буквы в каждой строке — худшее,
      что можно предложить. Компонент общий с загрузкой отчёта, а список
      рисуется в портале: карточка со скруглёнными углами (`overflow-hidden`)
      обрезала бы обычный выпадающий блок.
    - **ТАБЛИЦА СВЁРСТАНА ПЛОТНО** (правка 24.09.2026, просьба владельца:
      «в экселе данные легко помещаются на одном экране»). Здесь это не
      украшение: таблицу ведут построчно по выписке, и прокрутка вместо
      одного взгляда — это и есть работа, которой не должно быть.
      - **Высоту строки задаёт ТОЛЬКО поле ввода.** Своих вертикальных
        отступов у ячейки нет: два набора отступов — у ячейки и у поля
        внутри неё — складывались и давали строку вдвое выше нужного.
        Отсюда же правило: надпись внутри ячейки («сошлось», «завод не
        указан») обязана иметь ТЕ ЖЕ отступы и кегль, что поле, иначе
        текстовые строки встают выше строк с полем.
      - **«ИМПОРТ» И «ДОБАВИТЬ СТРОКУ» — СВЕРХУ, У ПРАВОГО КРАЯ** (просьба
        владельца 24.09.2026). Снизу они уезжали под последнюю строку, и до
        них приходилось листать всю таблицу — ровно та прокрутка, от которой
        её и уплотняли. Сверху они на месте всегда и стоят там же, где импорт
        у «Партнёров» и «Номенклатуры». Импорт рядом с «Добавить строку»: это
        два способа одного и того же. Под таблицей остались ТОЛЬКО ИТОГИ — им
        место как раз там, где строки кончились, это их сумма, а не действие;
        и полоса под таблицей не рисуется вовсе, когда итогов нет.
      - **КВАРТАЛ И МЕСЯЦ — В ОДНУ СТРОКУ, но через разделитель.** Двумя
        рядами они съедали полсотни пикселей высоты, ради которой всё и
        затевалось. Разделитель оставлен намеренно: квартал отвечает «какой
        отчётный период», месяц — «в какой выписке искать», и сливаться в
        один список эти вопросы не должны.
    - **СТРОКИ ВЫРОВНЕНЫ ПО ВЕРХУ, а не по середине** (замечание владельца
      24.09.2026). У валютных площадок под суммой стоит вторая строчка, и при
      выравнивании по центру вся строка уезжала вниз: поступление, НДС и завод
      переставали лежать на одном уровне с соседними строками — то есть
      главные числа таблицы читались вразнобой. Сверху они совпадают всегда,
      сколько бы строчек ни было ниже. Заодно таблица уплотнена (высоту
      задают сами поля ввода, а не ячейки), а валютная сумма набрана мельче:
      она для справки, и вровень с рублёвой спорила с ней за внимание.
    - **В ячейках суммы РАЗДЕЛЕНЫ ТЫСЯЧИ**, пока в поле не встали курсором
      (`MoneyCell`): «925 000,00» читается, «925000.00» пересчитывают пальцем.
      Как только поле правят, показывается то, что в нём лежит, — иначе
      пробелы прыгали бы под курсором. Сервер и так принимает «10 000,50».
      Курс и НДС не форматируются: это множители, тысяч в них не бывает.
    - **Суммы складывает СЕРВЕР** (итоги под таблицей): в JSON они строки, и
      считать их на экране нельзя. «Сумма завода» и «фактический завод»
      хранятся обе и ничего друг из друга не выводят — расхождение между ними
      и есть то, ради чего таблицу ведут; курс тоже ни на что не множится
      сам.
    - Право своё (`CAN_VIEW_PAYMENTS` / `CAN_MANAGE_PAYMENTS`), хоть пока и
      совпадает с отчётами: смотреть «что насчитали» и «что дошло» однажды
      будут разные люди.
  - **«Номенклатура» (`/finance`) — НАСТОЯЩИЙ КАТАЛОГ** (16.09.2026, заведён

    прав. Таблицы `tracks` и `track_rights`, роутер

    всего, будет не тот человек, которому положено видеть суммы выплат;
    разойтись этим правам — вопрос времени, и лучше они разойдутся в одну
    строку, чем будут вычленяться из финансов задним числом.
    - **ПРАВО ССЫЛАЕТСЯ НА КАРТОЧКУ КОНТРАГЕНТА** (`track_rights.contragent_id`,

      базой контрагентов его роднило только совпадение текста: 242 673 строки

      карточки рвало связь молча, а у одного лейбла в каталоге встречалось

      находилась только часть его треков. Считать по таким совпадениям
      выплаты нельзя. Неочевидное:

        дубликат, а то, как правообладатель записан в Dista, и по нему сверяют

        доли смежных), и калитка интерфейса их бы не пропустила. Решение

        деньги в отчётах, править их уже никто не будет». Для этого у
        `ops/import_tracks.py` есть флаг `--non-catalog` (он же выключает
        сверку долей — иначе отчёт об ошибках состоял бы из неё одной).
      - **Выгрузка идёт по открытому списку**: экспорт обязан отдавать то,
        что видно на экране, — здесь это верно и для выбора списка.
      - По умолчанию API отдаёт КАТАЛОГ (`in_catalog=true`): всё, что было
        залито до сих пор, — каталог, и старые вызовы продолжают работать
        как раньше.
    - **Ключ — артикул** (`tracks.sku`), наш внутренний код. В выгрузке он
      уникален на всех 121 529 строках, а ISRC на эту роль не годится совсем:
      11 643 повтора, и у 26 треков он просто 'TBA'. Тот же выбор, что у
      контрагентов с `dista_id`, и по той же причине: свой код уникален по
      построению, чужой идентификатор — нет.
    - **Права — СТРОКИ, а не нумерованные колонки.** В выгрузке это «Владелец
      авт.прав 1», «Доля(%) авт.прав 1», «Роялти(%) авт. прав 1», затем то же
      для второго и третьего: таблица растёт вправо и обрывается там, где у
      Dista кончились заготовленные колонки (третий слот занят у 32 треков). У
      нас ключ — тройка (трек, правообладатель, вид права), и четвёртый
      правообладатель не потребует ни миграции, ни новой колонки в таблице.
      Это модель из брейншторма по расчёту роялти.
    - **Доли лежат В ДВУХ МЕСТАХ и иногда противоречат друг другу.** У трека
      есть «Доля авторских прав» и «Доля смежных прав» (`share_author` /
      `share_related`), и отдельно — доли конкретных правообладателей в
      `track_rights`. У **45 617 треков доля смежных равна нулю, а владелец
      смежных указан со стопроцентной долей**. Что из этого правда, выяснится
      на живом квартальном отчёте (см. брейншторм, §3: как Dista отличает
      «наших авторских нет» от «не заполнено»), поэтому импорт хранит оба
      числа, а карточка показывает оба. Выбрать одно сейчас значило бы
      зашить догадку в данные — а догадку в коде показа поменять можно,
      потерянное при импорте значение уже нет.
    - **Доли и ставки приводятся к процентам ОДИН РАЗ, в импорте.** В
      выгрузке они лежат долями единицы (1 = 100%, 0.8 = 80%); если оставить
      как есть, на сто умножало бы каждое место показа, и однажды кто-нибудь
      забыл бы. Значение больше единицы импорт считает уже процентом и не
      трогает — если Dista сменит формат, каталог не получит молча доли по
      8000%. Наружу проценты уходят СТРОКАМИ («100», «33.33»), по той же
      причине, что и деньги: 33.33 в JSON-числе превращается в
      33.329999999999998.
    - **Импорт замещает состав прав целиком**, а не дополняет: строка
      выгрузки несёт полное состояние трека, и при слиянии ошибочно
      заведённого правообладателя нельзя было бы убрать никогда. Повторный
      прогон того же файла ничего не плодит (ключ — артикул). Треки не
      удаляются: исчезнувший помечается `archived_at`, и только по явному
      флагу `--archive-missing` — ежедневная выгрузка это несколько десятков
      строк, а не каталог целиком, и архивирование по умолчанию отправило бы
      в архив всё остальное.
    - **Галочка «учитывать регистр»** (17.09.2026) действует и на общий
      поиск, и на фильтр правообладателя: это один и тот же вопрос — считать
      ли «густ» и «ГУСТ» одним словом. По умолчанию выключена (человек ищет
      «густ», а в каталоге «ООО ГУСТ МЬЮЗИК»), но регистр иногда и есть сам
      вопрос: два написания Густ Мьюзик — это два разных правообладателя, и
      различить их без точного поиска нечем. На скорости не сказывается:
      триграммные индексы работают и с LIKE, и с ILIKE. При отборе по
      карточке галочка ни на что не влияет — там сравнивается ссылка, а не
      строки.
      - **В SQLite-прогоне это НЕ ПРОВЕРИТЬ, и это не пропуск в тестах:**
        его LIKE игнорирует регистр у латиницы и учитывает у кириллицы,
        причём одинаково при LIKE и ILIKE. То есть на нём ломается то одна
        ветка, то другая — по свойству движка, а не кода. Проверяется на
        проде, где Postgres.
    - **Рядом галочка «точное совпадение»** (17.09.2026) — и она про ДРУГОЕ:
      не как сравнивать буквы, а сравнивать ли строку целиком. Вместе с
      регистром они и дают способ развести «ООО Густ Мьюзик», «ООО ГУСТ
      МЬЮЗИК» и «Густ Мьюзик KZ», ради которого их и просили. Действует на оба
      поля — общий поиск и правообладателя — и уходит в выгрузку: экспорт
      обязан отдавать ровно то, что видно на экране.
      - **Сделано ТЕМ ЖЕ LIKE, только без «%»**, а не через `lower(col) = ...`:
        равенство с функцией не попадает ни в один наш индекс, а LIKE без
        подстановок попадает в триграммный. Скорость та же, что у поиска по
        подстроке.
      - **Подстановки в строке поиска экранируются** (`_escape_like`): человек,
        набравший «50%» или «mix_1», ищет эти символы, а не «что угодно
        после 50». В артикулах и названиях встречается и то и другое.
    - **ПОИСК ПО ПОДСТРОКЕ ИДЁТ ПО ОДНОЙ КОЛОНКЕ** `tracks.search_text` —
      склейке артикула, кода, названия и исполнителя через перевод строки,
      которую считает сама база (`Computed`, миграция `f4a6b2c98e71`,
      18.09.2026). Причина — ПЛАНИРОВЩИК: четыре ILIKE через OR, у каждого
      свой триграммный индекс, он оценивал дороже полного чтения таблицы и
      брал seq scan. Замер на проде: страница выдачи 803 мс, счётчик 509 мс;
      после правки — 17 мс и 2.7 мс. Заметно это стало с появлением
      неКаталога (таблица выросла на 11 тысяч строк), но дело было не в нём:
      индексы не работали с самого начала.
      - **Разделитель — перевод строки**, иначе поиск «100 FRX» находил бы
        трек, у которого артикул кончается на 100, а код начинается на FRX:
        склейка ищется целиком. Перевод строки в поле поиска не наберёшь.
      - **Колонку считает БАЗА, а не код**: иначе её пришлось бы обновлять в
        трёх местах (импорт из интерфейса, `ops/import_tracks.py`, ручная
        правка карточки), и однажды одно из них забыли бы — поиск молча
        перестал бы находить поправленный трек.
      - **Выражение живёт в одном месте** — `SEARCH_TEXT_SQL` в `models.py`,
        миграция берёт его оттуда же.
      - **«Точное совпадение» осталось по отдельным полям**: это вопрос про
        конкретное поле («артикул равен этой строке»), а не про склейку, и
        LIKE без подстановок отбирает считанные строки — план и так
        индексный.
      - **Добавляя новое поле для поиска, добавляйте его В СКЛЕЙКУ** (то есть
        миграцией), а не пятым условием через OR: пятое условие вернёт всё
        туда же, откуда ушли.
      - **Фильтр правообладателя (~370 мс на «густ») — это не та же беда**:
        там триграммный индекс работает, а время уходит на соединение с
        13 872 найденными треками. Столько строк — это и есть ответ.
    - **Поиск — одним полем по четырём** (артикул, ISRC/UPC, название,
      исполнитель): человек со строчкой отчёта в руках не знает заранее, код
      у него в руках или название. Правообладатель — поле ввода, а не список:
      их 729, такой список листают дольше, чем набирают фамилию. Каталог —
      выбор из 502 значений, и справочник считается ПО ДАННЫМ, а не задан в
      `tags.py`: это поле Dista, любой зафиксированный список разошёлся бы с
      ним на первом же импорте.
    - **АВТОРСКИЕ ПРАВА ВСЕГДА ПЕРВЫЕ, смежные вторые** (просьба владельца
      17.09.2026) — и в таблице каталога, и в карточке трека. Порядок один и
      тот же в обоих местах намеренно: человек ходит из списка в карточку и
      обратно, и всякий раз перечитывать подписи, чтобы понять, где чьи доли,
      он не должен.
    - **В таблице только то, по чему трек опознают**: артикул, ISRC/UPC,
      название, исполнитель и права. Автор слов/музыки, альбом, жанр, каталог,
      доли уровня трека и дата прав — в карточке, которая открывается
      нажатием на строку (просьба владельца). Исполнитель при этом ОТДЕЛЬНАЯ
      колонка, а не подпись под названием: по нему ищут, и колонку глаз
      проходит сверху вниз, а подпись — нет.
    - Пустая ячейка прав подписана СЛОВАМИ («наших долей нет»), а не
      прочерком: прочерк читается как «не заполнено», а это противоположный
      случай — у кавера наших авторских законно нет.
    - Единственная настоящая `<table>` в проекте (везде остальное — сетки из
      div'ов): колонки разной ширины и зависят от содержимого, а обёртка со
      скроллом нужна, чтобы на узком экране таблица уезжала вбок, а не
      схлопывала колонки.
    - **Выгрузка всего каталога занимает около 80 секунд** — и это не
      недосмотр, а цена записи 3.6 миллиона ячеек в .xlsx. Первый вариант
      собирал файл 93 секунды на объектах ORM; переписали на колонки — стало
      79, то есть узкое место в самом openpyxl, а не в запросе. Выгрузка по
      фильтру мгновенная (0.2 с), а она и есть обычный сценарий: выгрузили
      кусок, поправили, залили обратно. В модалке об этом сказано словами —
      иначе человек решит, что кнопка не сработала, и нажмёт ещё раз.
    - **КАРТОЧКУ ТРЕКА МОЖНО ПРАВИТЬ РУКАМИ** (17.09.2026, просьба
      владельца): все метаданные, состав правообладателей, доли и ставки.
      `PATCH /nomenclature/{id}`, право своё — `CAN_EDIT_NOMENCLATURE`
      (admin и director; шире импорта, потому что файл переписывает сотни
      треков вслепую, а карточку правят по одной, глядя на неё).
      - **Компромисс с импортом открытый: правка держится до следующего
        импорта ТОГО ЖЕ артикула.** Строка файла несёт полное состояние трека
        и не спрашивает, правил ли кто-то карточку руками. Иначе пришлось бы
        завести у каждого поля признак «правили руками, не трогать» — то есть
        второй источник правды в каждой ячейке. Правка нужна, чтобы поправить
        позицию здесь и сейчас, а не чтобы вести каталог в обход Dista.
      - **СВЕРКА ДОЛЕЙ СО СПРАВОЧНЫМИ ОБЯЗАТЕЛЬНА**: сумма долей
        правообладателей должна совпадать с общей долей трека, отдельно по
        авторским и смежным. Проверку делает `check_shares` — ТОТ ЖЕ код, что
        проверяет файл импорта (вынесен в `nomenclature_import` вместе с
        `check_required`). Разойдись эти две калитки, и руками заводилось бы
        то, что импорт принять отказывается.
      - **Исторические расхождения это не чинит, но и сохранить их заново не
        даёт.** 45 617 треков с нулевой общей долей смежных при владельце со
        стопроцентной лежат как лежали; но если такую карточку открыли и
        правят — сохранить её можно только сходящейся. Поправить разрешено с
        любой стороны, и доля правообладателя, и справочная доля трека — оба
        поля в одной форме, а кнопка «взять сумму» ставит справочную равной
        сумме долей.
      - **Сверка считается в браузере на каждый символ** и показана над
        кнопкой сохранения: сервер несходящуюся карточку не примет, и узнавать
        об этом в момент нажатия «Сохранить» — узнавать поздно.
      - **Состав прав замещается целиком**, как при импорте: присланный список
        и есть новое состояние, а слоты нумеруются заново. Номер слота не
        значит ничего, кроме порядка показа.
      - **Больше трёх правообладателей на вид права — отказ.** В выгрузке
        Dista под них отведено три места, и четвёртый молча не попал бы в
        экспорт (`_rights_cells` пишет фиксированные 18 ячеек). Отказ честнее
        тихой потери строки; понадобится четвёртый — расширять надо формат
        файла, а не молчать.
      - **Незнакомое имя правообладателя — не ошибка, а вопрос**: сервер
        отвечает 409 `{code:'unknown_owners', owners:[…]}` со списком и
        подсказками («может быть, это…», те же три способа поиска похожих, что
        у импорта), и заводит пустые карточки только по явному
        `create_missing_owners`. Молчаливое заведение означало бы, что опечатка
        в имени создаёт новую карточку, мимо которой уйдут деньги.
      - **`source_file` и `imported_at` правка НЕ трогает**: они отвечают на
        вопрос «из какой выгрузки приехала строка», и ручная правка этого не
        меняет. Кто и что поправил, отвечает журнал — `nomenclature.track.update`
        с перечнем полей поимённо.
    - **Импорт и экспорт — в интерфейсе** (17.09.2026). Экспорт отдаёт файл в
      ТОМ ЖЕ формате, что и Dista (те же 30 колонок, доли правообладателей
      снова долями единицы), с учётом текущих фильтров: выгрузили, поправили,
      залили обратно. Симметрия проверена тестом — наш экспорт заливается
      нашим же импортом без единой ошибки; на этом, кстати, и поймали, что
      дату надо писать датой, а не строкой.
    - **ВСТАВКА ИЗ БУФЕРА (Ctrl+V) — второй источник импорта** наравне с
      файлом (17.09.2026, просьба владельца; так же устроен «Буфер обмена» в
      окне импорта Dista). Ежедневная порция — несколько десятков строк, и
      ради них сохранять файл из Excel лишнее движение. Excel и грид Dista
      кладут таблицу в буфер ТЕКСТОМ С ТАБУЛЯЦИЯМИ, поэтому разбираем
      csv-читателем с разделителем-табуляцией: ячейка с переводом строки
      внутри берётся в кавычки, и наивный split её разорвал бы.
      - **Форматов ячеек в буфере нет** — там только то, что человек видел на
        экране. Поэтому проценты приходят со знаком («80%»), и `share_percent`
        считает их процентами; число без знака — тоже процент, как в обычном
        файле. Знак процента при этом сильнее формата ячейки: «80%» не
        умножается на сто ни при каких обстоятельствах.
      - Ctrl+V слушает ОКНО, а не поле ввода: своих текстовых полей в модалке
        нет, и заставлять человека сперва попасть курсором в прямоугольник —
        ровно та возня, от которой вставка избавляет. Текст без табуляций
        пропускается молча: это не таблица, и перехватывать чужую вставку
        незачем.
      - Вставка, в которой НИ У ОДНОЙ строки нет артикула, отвергается
        понятной фразой, а не сотней одинаковых ошибок в предпросмотре:
        значит, скопировали не то.
      - У треков из буфера в источнике так и написано — «буфер обмена»:
        имени файла тут нет и придумывать его нельзя.
    - **Импорт В ДВА ШАГА: «проверить» → «применить».** Сервер сначала читает
      файл и показывает, что получится, и только потом пишет. Иначе человек,
      заливающий файл ежедневно, не видел бы, что применение ЗАМЕЩАЕТ состав
      прав у каждого трека из файла.
    - **ДОЛИ И СТАВКИ — ПРОЦЕНТЫ 0–100, а решает ФОРМАТ ЯЧЕЙКИ** (17.09.2026).
      В файлах два вида записи, и отличаются они не величиной: у выгрузки
      Dista ячейка процентная («0%»), внутри лежит доля единицы (0.8 = 80%);
      у файла, собранного руками, обычное число (70 = 70%). Первый вариант
      импорта гадал по величине — «больше единицы значит процент» — и на
      нормальном файле владельца сыпал предупреждениями на каждую строку.
      Гадать нельзя в принципе: 1 — это и 100%, и 1%, разница только в
      оформлении ячейки. Экспорт при этом пишет ПРОЦЕНТЫ обычными числами:
      читаем оба вида, пишем один, понятный человеку, который правит файл.
    - **Шапка узнаётся по содержимому, а не по номеру строки**: файл от Dista
      начинается с подписей колонок, а собранный руками — сразу с данных, и
      пропускать первую строку вслепую значит терять первый трек. Заодно так
      отсекается шапка, попавшая в середину файла.
    - **Предпросмотр — ТАБЛИЦА, а не список ошибок** (по образцу окна
      предпроверки в Dista, скриншот владельца). Человеку надо видеть, что и в
      какую колонку попало: что «0.8» понято как 80%, что имя правообладателя
      не съехало на соседнее место. Список претензий без самих данных
      читается как приговор без дела. У каждой строки галочка «Ок» — её можно
      снять и не заливать строку (номера снятых уезжают в `skip_rows`), у
      ошибочных она недоступна. Показываются первые 200 строк: больше глазами
      никто не проверяет, а браузеру каждая строка — это тридцать ячеек.
      **Пустые места правообладателей в таблицу не попадают** (правка
      17.09.2026): если во всём файле нет вторых и третьих, их восемнадцать
      столбцов превращались в пустоту, и таблицу приходилось листать вбок.
      Занятость считается ПО ВСЕМУ ФАЙЛУ, а не по показанным двум сотням
      строк, — иначе колонка исчезла бы из-за того, что второй
      правообладатель встречается лишь на пятисотой строке. Первое место
      показывается всегда: без него непонятно, куда вообще попадают
      правообладатели. **Замечание пишется ПОД строкой**, а не колонкой
      справа: колонка уезжала за правый край, и до причины надо было листать.
      **«Не пройдёт: N» — КЛИКАБЕЛЬНО** (правка 18.09.2026): нажатие
      показывает в той же таблице ВСЕ непроходящие строки, отдельным списком
      с сервера (`error_preview`, до 2000). Раньше их было не найти вовсе:
      в первых двухстах строках файла их может не быть ни одной — в боевом
      файле владельца не проходило 309 позиций, и ни одна не попадала в
      предпросмотр.
    - **Что проверяется** (правила владельца 17.09.2026): обязательны дата
      прав, артикул, наименование, исполнитель и обе общие доли; **сумма
      долей правообладателей обязана совпадать с общей долей трека**, отдельно
      по авторским и смежным; второго и третьего правообладателя может не
      быть — это норма. Код/ISRC, автор слов и музыки и альбом необязательны:
      альбом заведён в базе отдельным артикулом, и у него нет ни кода, ни
      авторов, а сингл не входит ни в какой альбом. Каталог, жанр и общая
      ставка роялти НЕ обязательны, хотя формально стоят в файле до
      правообладателей: в боевой выгрузке жанр пуст у 95.6% строк, ставка — у
      75.4%, каталог — у 22.5%, и требовать их значило бы отвергать почти весь
      настоящий каталог.
    - **Старая выгрузка не сходится по суммам долей — ПРИНЯТО КАК ЕСТЬ**
      (решение владельца 17.09.2026). В залитом каталоге правило выполняется
      у 117 156 треков из 121 528 по авторским правам и у 77 229 по смежным;
      остальное — это 45 617 треков с нулевой общей долей смежных при
      владельце со стопроцентной и 3 478 наоборот, с общей долей и без
      владельца. Чинить эти строки и перезаливать каталог не будем: данные
      исторические, а разбираться с ними всё равно придётся на стороне Dista.
      Отсюда три следствия, которые легко перепутать:
      - **проверка остаётся строгой для НОВЫХ файлов** — свежая выгрузка
        владельца (пример от 17.09.2026, 68 строк) проходит её без единой
        ошибки, значит, требование выполнимо и ослаблять его незачем;
      - **историю по-прежнему заливает скрипт** `ops/import_tracks.py`: он
        грузит всё и лишь рассказывает об ошибках. Если тот же файл занести
        через интерфейс, эти 48 тысяч строк не пройдут — и это не поломка, а
        разница политик, ради которой флаг `--strict` и существует;
      - **уже залитые строки никуда не денутся**: импорт правит только те
        треки, что есть в файле.
      Строки с ошибками ПРОПУСКАЮТСЯ, а не роняют файл: из-за одной кривой
      доли незачем откладывать остальные.
    - **Правообладатель сверяется с базой контрагентов.** Имя из файла
      сравнивается с титлами карточек и с именами, уже встречавшимися в
      каталоге (в боевом каталоге 724 имени из 729 совпадают с титлом буква в
      букву). Похожее — предлагается к замене, и по умолчанию замена включена:
      дубль правообладателя дороже лишнего нажатия. Незнакомое — предлагается
      завести карточкой контрагента (пустой, с одним титлом: остальное
      заполняют в ML Docs, до тех пор карточка честно красная).
    - **Похожесть ищется тремя способами подряд** (`normalize_owner` и
      `OwnerIndex.match` в `app/nomenclature_import.py`): совпадение после
      нормализации (регистр, пробелы, точки, форма собственности, приписка KZ
      — «ИП Анненков М.В.» против «Анненков М.В. (ИП)»), затем «одно имя —
      начало другого» («ИП Погорельских» против «Погорельских А.А. (ИП)»), и
      только потом опечатки — по похожести строк. Всё это ПОДСКАЗКА: замену
      подтверждает человек, который видит оба написания. Сами такие пары в
      каталоге есть — 11 групп на 729 имён.
    - **Разбор файла ОДИН на два входа** (`app/nomenclature_import.py`):
      им пользуются и импорт из интерфейса, и серверный `ops/import_tracks.py`.
      Разойдись они в округлении доли или в списке обязательных полей — и
      каталог, залитый скриптом, отличался бы от залитого из интерфейса.
      А вот ПОЛИТИКА у них разная и намеренно: интерфейс — ежедневная калитка
      и строку с ошибкой не пропускает, скрипт — заливка исторических данных
      «как есть», он про ошибки рассказывает, но грузит всё (строгость
      включается флагом `--strict`).
    - Импорт из интерфейса ограничен 20 000 строк: каталог целиком (121
      тысяча) заливают скриптом, разбор такого файла занимает минуты, и
      держать всё это время открытым HTTP-запрос незачем. В журнал действий
      идёт ОДНА запись на прогон (`nomenclature.import`), а не на каждый
      трек.
    - **Исполнитель в таблице набран так же, как название** (просьба
      владельца 17.09.2026): это одинаково важные опознавательные знаки
      трека. Приглушённым он читался как пояснение к названию, хотя ищут чаще
      именно по нему.
    - **Сами выгрузки в git не коммитятся** (`.gitignore`): это боевые данные
      лейбла и десятки мегабайт, а git хранит каждую версию навсегда.
  - **Связка с Dista (`dista_id`) показывается в карточке ML Finance, а не
    ML Docs** (17.09.2026, решение владельца: «ML Docs теперь с Dista не
    связан»). ML Docs — про договоры и шаблоны; каталог, деньги и сверка с
    Dista живут в финансах, туда же переехала и строка связки. Поле в базе
    никуда не делось и остаётся ГЛАВНЫМ КЛЮЧОМ ИМПОРТА контрагентов — колонка
    «Dista ID» в файле импорта/экспорта на месте, менять формат файла ради
    переезда строки в интерфейсе незачем. Рядом с ней в карточке и «исключён
    из Dista»: это решение человека, а не пробел в данных, и показывать его
    как пусто нельзя.
  - **«Dista Connect» переехала сюда из ML Docs.** Сверка нашей базы с
    выгрузкой Dista Music — работа про контрагентов, а не про договоры. Право
    прежнее (`CAN_USE_DISTA_SYNC`, только admin), маршрут тоже прежний
    (`/dista`): менять адрес ради переезда пункта меню значило бы ломать
    сохранённые ссылки. Директор ML Finance видит, а этой вкладки в нём — нет.
  - **В обоих продуктах вкладка называется «Контрагенты»** (переименование
    16.09.2026: в ML Docs она звалась «База контрагентов»). Это одно и то же
    место с одним и тем же списком, и разные имена заставляли человека,
    переключающего продукты, гадать, два это раздела или один. Маршруты
    остались прежними и РАЗНЫЕ — `/database` в ML Docs и
    `/finance/contragents` в ML Finance, страницы тоже разные
    (`DatabasePage` / `FinancePage`): совпадает подпись, а не экран. Менять
    URL ради подписи незачем — то же решение, что у «Шаблонов» на
    `/folders`.
  - **База контрагентов ОДНА.** ML Finance не заводит своих карточек и не
    копирует чужие: список строится ТЕМ ЖЕ `search_contragents`, что и «База
    контрагентов» (`routers_finance.py` вызывает его напрямую), только к
    каждой строке добавляется баланс. Разойдись они в поиске или пагинации — и
    один и тот же человек находился бы в одном продукте и не находился в
    другом. Карточки заводят и правят по-прежнему в ML Docs.
  - **Баланс НЕ ХРАНИТСЯ** — считается суммой операций (`app/finance.py`:
    `balances` на страницу списка одним запросом, `totals` на карточку).
    Хранимая колонка была бы вторым источником правды: её надо пересчитывать
    при каждой правке, и она тихо разъезжается с операциями в тот день, когда
    кто-то поправит строку мимо приложения. Операций у контрагента десятки, не
    миллионы. То же решение, что у кубка и достижений.
  - **Сумма всегда положительная, знак несёт `kind`** ('income' / 'expense').
    Иначе «вернули аванс» записывается двумя способами, и любой отчёт по
    расходам приходится считать с оговорками. Ноль и минус сервер не
    принимает.
  - **Деньги — `Numeric(14,2)` в базе и СТРОКИ в JSON.** float в JSON — тот же
    двоичный дробный тип: `1234.10` уезжает в `1234.0999999999999`. Фронт
    суммы не парсит и не складывает, он их показывает; всё, что надо
    посчитать, считает сервер. Ввод, наоборот, принимается как напечатали:
    «10 000,50» с пробелами и запятой разбирает `_parse_amount`.
  - **Валюта одна — рубль** (решение владельца). В базе есть казахстанские
    контрагенты, но суммы по ним приводят к рублям при вводе. Колонки валюты
    нет СОЗНАТЕЛЬНО: без курсов и даты курса она создаёт видимость
    мультивалютности, которой нет — складывать тенге с рублями всё равно
    нечем. Понадобится вторая валюта — это колонка `currency` плюс отдельный
    баланс на каждую, а не пересчёт задним числом.
  - **Правки операции нет вовсе, только удаление и ввод заново**, и удаляет
    Admin (`CAN_DELETE_FINANCE_OPERATIONS`); вносят оба
    (`CAN_ADD_FINANCE_OPERATIONS`). Денежная строка, которую можно молча
    переписать, — не история, а черновик. Внесение и удаление пишутся в
    `audit_log` (`finance.operation.create` / `.delete`) с суммой и
    категорией — по ним видно, кто внёс операцию, даже если строку удалили.
  - **`occurred_on` и `created_at` — РАЗНЫЕ даты.** Когда операция произошла и
    когда её занесли; заносят регулярно задним числом.
  - **Контрагента с операциями НЕ УДАЛИТЬ**: `ondelete='RESTRICT'` плюс
    проверка в `delete_contragent`, отвечающая 409 с понятным текстом. Каскад
    означал бы, что удаление карточки молча стирает денежную историю, а без
    проверки БД вернула бы 500 про внешний ключ, из которой оператор не понял
    бы ничего.
  - **Категорий ДВА СПРАВОЧНИКА, по одному на вид операции**
    (`INCOME_CATEGORIES` / `EXPENSE_CATEGORIES` в `app/finance.py`, уезжают в
    `GET /tags` рядом со странами и типами). Приходят только квартальные
    отчёты площадок («Квартальный отчёт»), уходят выплаты артисту («Выплата
    роялти», «Выплата аванса»). Общий список позволил бы выбрать «Выплату
    аванса» у поступления — не редкую ошибку, а бессмыслицу, которую потом
    ищут в отчёте; поэтому категория проверяется ПРОТИВ ВИДА операции, а не
    против общего набора. Когда у вида категория одна, форма показывает её
    строкой, а не списком из одного пункта — и сама станет селектом, как
    только появится вторая.
  - **У поступления ОБЯЗАТЕЛЕН ПЕРИОД — за какие кварталы деньги**, у расхода
    его нет вовсе (переданный отвергается, а не проглатывается). Причина:
    квартальный отчёт относится к кварталу, а не к дате зачисления — за I
    квартал платят в апреле, — и одним платежом нередко закрывают несколько
    кварталов сразу. Отсюда пара «с» и «по».
    - Хранится ЧЕТЫРЬМЯ маленькими числами (`period_year_from`,
      `period_quarter_from`, `period_year_to`, `period_quarter_to`), а не
      строкой «2026-Q1» и не датами: строку пришлось бы разбирать везде, где
      нужно сравнение, а даты выглядели бы точнее, чем есть — «с 01.01 по
      31.03» человек не вводил, и первый же отчёт по кварталам начал бы
      угадывать их обратно.
    - **У одного квартала начало и конец СОВПАДАЮТ**, а не «конец пустой»:
      иначе случай «пусто = один квартал» пришлось бы разбирать в каждом
      читающем месте. Клиент вправе не слать конец — сервер продублирует
      начало сам.
    - Подпись периода («I кв. 2026», «IV кв. 2025 — II кв. 2026») собирает
      СЕРВЕР (`period_label`): формат — такое же правило, как правило знака
      суммы, и разъезжаться ему между экраном и будущей выгрузкой незачем.
    - Колонки nullable, обязательность живёт в приложении (`_parse_period`):
      NOT NULL в схеме запретил бы и расходы тоже.
  - Чего ML Finance НЕ делает: не считает роялти, не связывает операции с
    документами и не знает про периоды начислений. Здесь ручной учёт — что
    внесли, то и в балансе.

  прежний механизм убран целиком). У каждого в шапке значок 🔔 с числом
  непрочитанных; вкладка «Уведомления» осталась только у админа и стала
  местом, где их ПИШУТ (`CAN_SEND_NOTIFICATIONS`). Таблицы `announcements`
  (текст, автор, дата) и `announcement_recipients` (кому адресовано и
  прочитано ли). Неочевидное:
  - **Заголовок обязателен** (16.09.2026): в панели уведомления лежат
    списком, и по первым словам текста не всегда понятно, о чём объявление.
    Колонка `announcements.title` при этом NULLABLE — у отправленных до этой
    даты заголовка нет и взяться ему неоткуда, придумывать за автора значило
    бы подписать его словами, которых он не писал; такие показываются как
    раньше, одним текстом. Обязательность живёт в `NewAnnouncement`, а не в
    схеме: NOT NULL потребовал бы DEFAULT '' для истории, то есть тот же
    пустой заголовок, только неотличимый от заполненного. Под заголовком
    отступ в пустую строку (`mb-4`): заголовок и текст должны читаться как
    две разные вещи, а не как абзац с потолстевшей первой строкой.
  - **Адресаты — строками на каждого, а не флагом «всем».** Так «прочитали
    3 из 7» считается COUNT'ом, а не угадывается; состав получателей
    фиксируется НА МОМЕНТ ОТПРАВКИ (сотрудник, заведённый завтра, не увидит
    вчерашнее объявление, а отключение человека не переписывает список
    задним числом); и «всем», и «выбранным» хранятся одинаково, читающий код
    не разветвляется.
  - В адресаты не попадают отключённые (читать некому) и сам автор. Если
    после этих отсечений никого не осталось — 400, иначе объявление молча
    уходило бы в пустоту.
  - **Панель ВЫПАДАЕТ ИЗ ЗНАЧКА, а не открывается модалкой** (правка
    16.09.2026, `layout/NotificationsPanel.jsx`). Уведомление — это взгляд
    вскользь, а модалка гасит экран и требует себя закрыть, то есть ведёт
    себя как дело, которым надо заняться. Состояние панели живёт в
    `Header`, а не в стеке модалок: она привязана к кнопке, из которой
    появилась. Закрывается нажатием мимо, Escape и повторным нажатием на

    обработчик закрывал бы панель и тут же открывал заново. Монтируется
    только открытой, поэтому список запрашивается при каждом открытии, а не
    висит с прошлого раза. Модалка `NotificationsModal` УДАЛЕНА: два экрана
    одного и того же разошлись бы при первой правке.

    панели, а док черновика в правом нижнем углу живёт на `z-40` и при
    прежнем `z-10` накрывал бы её нижний край. Выше остаются подсказки
    `ComboCell` (z-50) и модалки (со 100) — им и положено перекрывать шапку.
  - **Открытие панели и есть прочтение**: `POST /notifications/read`
    отмечает всё разом. Пометки «новое» при этом остаются видимыми — они
    посчитаны по ответу, пришедшему ДО отметки.
  - **Чтение не имеет отдельного права**: эндпоинты отдают строки текущего
    пользователя, и параметра «чьи» у них нет вовсе — подсмотреть чужие
    нечем. Право есть только на «написать».
  - **Два разных удаления.** Получатель убирает уведомление У СЕБЯ
    (`DELETE /notifications/mine/{id}`) — это ПОМЕТКА `hidden_at` на его
    строке, а не удаление: строка держит и «кому адресовано», и «прочитал
    ли», снеси её — у админа молча уменьшился бы знаменатель «3 из 7», а
    человек пропал бы из списка, будто ему и не отправляли. Админский
    `DELETE /notifications/{id}` сносит объявление целиком и у всех

    вечно.
  - Порядок маршрутов: `/count`, `/read`, `/sent` зарегистрированы РАНЬШЕ
    `/{id}` — иначе FastAPI попробует разобрать «sent» как uuid и вернёт 422
    (та же грабля, что с `/import` и `/export` у контрагентов).
  - **Что здесь было раньше.** Вкладка показывала предложения дозаполнить
    карточку контрагента значениями из формы генерации (`card_suggestions`,
    `app/suggestions.py`, захват в `generate_document`). Признано
    бесполезным и удалено вместе с кодом. **Таблица `card_suggestions`
    осталась в базе нетронутой** — удалять историю ради смены экрана
    несоразмерно; вернуть логику можно из git.

## Чего не делать

- Не выкладывать React поверх `backend/static/index.html`.
- Не забывать `./deploy.sh` перед коммитом, если менялся фронт — иначе на проде
  останется старая сборка при свежих исходниках.
- Не пушить только в один remote.
- Не вызывать `init_db()`/`create_all()` на сервере — только alembic (уже был инцидент:
  create_all создал таблицы до миграции, и `alembic upgrade` упал на «relation already exists»).
- Не хардкодить на фронте то, что отдаёт `GET /tags`.
- Не добавлять поля формы генерации в код фронта — они приходят из .docx.
- **Не заниматься мобильной вёрсткой** (решено 16.07.2026). Фронт свёрстан под десктоп
  сознательно: на весь проект три адаптивных класса, и это не недосмотр. У всех
  менеджеров есть ПК, с телефона сервисом не пользуются. Если открыть с телефона —
  вёрстка съедет (особенно форма генерации: `EditableTable` с `tableLayout: fixed`
  внутри `overflow-hidden` схлопывает колонки), и это ожидаемо. Не предлагать
  брейкпоинты, заглушки «откройте на ПК» и адаптацию таблиц, пока не попросят явно.
